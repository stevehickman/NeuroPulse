text: - [ ] **`OI-PRIV-48` (raised 2026-11-21, GitHub #971; privacy review of `infra/`, Finding I3, checked; `infra/posthog/erase_relay.py` `do_POST`, `ClickHouseEraser.erase`; `REQ-SW03-19`, `REQ-SW03-22`, `REQ-SW03-34`; `UC-096`) — anyone can starve the erasure relay, and each request it accepts costs a full mutation.** (1) `bucket.take()` runs before the body is parsed, so malformed requests spend the one bucket the whole service has (5 a second, burst 20, `UC-096`). A caller sending 5 a second keeps every real withdrawal at `429` for as long as it likes. The app keeps the ID and asks again at its next launch (`REQ-SW03-19`), and the 30-day TTL (`REQ-SW03-34`) still removes the events, so the policy holds while the TTL holds; the active erasure is what is defeated. (2) Each well-formed ID, real or random, runs `ALTER TABLE … DELETE` at once, a mutation that rewrites the parts it touches, so random well-formed IDs at the allowed rate load ClickHouse with mutations. The bucket is global because Caddy withholds the address, which is deliberate: a per-caller limit would need it. **Repair proposed:** validate before taking a token; queue accepted IDs durably and run one batched delete (`distinct_id IN (…)`, or a lightweight `DELETE` where the pinned version has one) per interval. Answering `200` when an ID is queued rather than deleted changes what `200` means in `REQ-SW03-19` ("deleted, or there were none"): a decision. **Closes when:** the relay cannot be starved by requests it refuses, and its deletes are batched or the cost is shown acceptable on a real stack. **Decided 2026-11-24 (the principal; option B; written in `NP-ANALYTICS-001` §7.6).** A new `202` means "queued", and `200` keeps its meaning, "deleted, or there were none". The relay validates before taking a rate-limit token, queues accepted IDs durably, answers `202`, and deletes the queue in batches; the queue holds pending IDs only, and no list of erased IDs is kept. **Order of release:** the app drops an ID only on `200` and treats `202` as keep-and-go-on, and ships before any relay sends `202`, because today's app drops on any `2xx` (`AnalyticsErasureQueue.kt`, `REQ-SW03-19` (b)). **App half built 2026-11-24** (`AnalyticsErasureQueue`, `ResearchAnalyticsGate`; `REQ-SW03-19` (b), (d), (e) amended; tested in `AnalyticsErasureTests`): only `200` drops an ID, `202` keeps it and the drain goes on, another `2xx` keeps it and the rest wait, and in a device erase or clear, where nothing can keep the ID, a `202` counts as accepted. No Swift or web copy of the queue exists. **Relay half built 2026-11-25** (`infra/posthog/erase_relay.py`; `REQ-SW03-22` (a) to (f) rewritten; `ci/test_posthog_erase_relay.py`, 28 cases and seven mutants, against a fake store): a request is validated before it takes a rate-limit token; an ID already queued is `202`; otherwise the store is asked whether it holds events under the ID, and none is `200` while some is queued on disk and then `202`; a worker deletes the queue in batches, one `ALTER … DELETE … IN` per table with `mutations_sync=2`, and an ID leaves the queue only after its batch succeeded. The batch figures (60 s, 500 IDs, 600 s) are `UC-210`. **A build choice for the principal to confirm:** answering a later ask without a list of erased IDs means checking the store, so `np_erase` may now also read the events table's `distinct_id` column. Whoever holds that password can list the pseudonymous IDs the store holds. The alternative is a short-lived list of erased IDs kept until the app has been told `200`, which the decision ruled out. **Still open:** confirming that choice; running the relay on a real stack (`OI-ANALYTICS-01` (2), with `--self-check`, which now also exercises the column grant); and deploying it only where no app older than the app half is in use. **Closes when:** the relay has run on a real stack and the choice above is confirmed. **Update 2026-11-26 (the principal):** the grant question waits on `OI-ANALYTICS-03` and is not settled now. The narrower design, a parameterized `SQL SECURITY DEFINER` view, does not work on the pinned ClickHouse 23.12 (views before 24.2 need read access to the table behind them; parameterized views gained `DEFINER` in 24.10), and it becomes the design when the rebuilt stack runs PostHog's ClickHouse (26.9 today). Until then the column grant stays as built.
