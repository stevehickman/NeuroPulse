text: - [ ] **`OI-PRIV-76` (raised 2026-11-22, from closing `OI-PRIV-53`; `REQ-SHDR-11` (c); `NP-INFRA-001` §3.4; `ci/shdr/shdr_fleet_schema.sql`) — the fleet database still records insert order in every row's `xmin` and `ctid`.** Schema Rev G removed the explicit sequences, but PostgreSQL gives every row a transaction ID (`xmin`, assigned in commit order across the whole database) and a physical position (`ctid`, roughly insert order until rows are rewritten), and anyone who can run SQL on the fleet database reads both. So the same thing `OI-PRIV-53` closed for the `id` column still holds one level down: within a month, `xmin` orders every device's dockings and groups one docking's rows in every table, and an outside time anchor (ingest logs, WAL or backup times) turns the order into roughly day-level time. Freezing keeps the `xmin` value, and `VACUUM FULL` or `CLUSTER` keep `xmin` while rewriting `ctid`. Nothing in the repository can fix this, because the ingest service does not exist yet (`OI-FLEET-01` (e)). **The design to build with it:** the ingest stages what it receives and writes it to the SHDR tables in batches, each in one transaction and in random order (`INSERT … SELECT … ORDER BY random()`), so the rows of a batch share one `xmin` and their physical order carries nothing; the batch is at least a month, or a count large enough that one batch spans many devices; the staging area holds the record only until the batch is written and keeps it nowhere else; and the database's own logs keep no statement text (`log_statement = none`). Read access to the fleet database is limited to the people who run it, with an audit trail. **Closes when:** the ingest is built that way, shown on a test database (`xmin` and `ctid` order within a batch say nothing about which device docked first), and `NP-INFRA-001` §3.4 states the batching as the deployment rule. Owner: Software. **Update 2026-11-25 (`REQ-SHDR-12`): the batch writer is built and shown; the ingest that calls it is not, so this stays open.** **Built:** `infra/fleet/ingest/shdr_batch_writer.sql`, loaded after the schema. The ingest stages each record in an unlogged per-month table in schema `np_stage` (closed to `PUBLIC`, carrying the targets' CHECKs); after the month ends `np_batch_flush(<month>)`, in one transaction, writes the month into the SHDR tables in random order, sets every month column to the batch month, merges a device that docked more than once by its own counters (`GREATEST` on grow-only counters, derived fields from the newest upload by those counters, a re-delivered record written once, a record for an unknown device counted and dropped), and drops the month's staging. A failure writes nothing and keeps staging; an open month is refused. **Shown** by `ci/test_shdr_batch_writer.py` on a live PostgreSQL (CI `shdr-schema-ci.yml`, 11 tests): 984 dockings from 400 devices share one `xmin`, and Spearman's rho between arrival order and `ctid` order is within ±0.04 for records, for first-docked device and for the `devices` table, against a limit of 5/sqrt(n-1) derived from the null distribution. The `--self-test` shows the same checks report rho 1.0 for a writer that commits each upload and for one transaction without the shuffle. **Ruled in the design, not left as a choice:** the batch is a calendar month, not a count. A month batch's `xmin` says exactly what `ingest_month` says; a count would close a batch partway through a month and place every row before or after a moment set by traffic. The size follows from `REQ-SHDR-11`'s month, so no register row. **`NP-INFRA-001` §3.4 item 5** states the batching as the deployment rule. **Left:** (1) the ingest service that parses the SHDR record, stages it and runs the monthly flush (`OI-FLEET-01` (e)); (2) merge rules for the five tables the writer refuses to stage (`module_inventory`, `socket_life`, `socket_part_type_wear`, `consumable_counts`, `module_rotation_advice`; reasons in `np_batch_unsupported_tables()`); until then nothing may write them upload by upload; (3) **a decision:** unlogged staging keeps arrival order out of the WAL, archives, replicas and base backups, but a server crash empties it and loses the open month's records, which the phones will not resend. Accept that loss, or name a durable staging that keeps arrival order out of the WAL; (4) deployment facts no test here can show: `log_statement = none`, `np_stage` readable by the ingest role only, read access to the fleet database limited and audited; (5) while a month is open its staging still shows that month's arrival order to whoever can read `np_stage`; (6) for tables with no natural key (`power_telemetry` and others) a client retry inside a month writes the record twice, as an unbatched ingest would. **Closes when:** (1) is built on the writer, (2) is ruled for each table, (3) is decided, and (4) is recorded for the deployment.
