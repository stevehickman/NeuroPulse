text: - [x] **`OI-PRIV-72` — ✅ CLOSED 2026-11-23 (raised 2026-11-23, follow-up to `OI-PRIV-24` (NP-PRIV-ANALYSIS-004); checked; `CLAUDE.md` §5.1 rule 2, §23; `REQ-FWHUB-81` (c), (f); `hub_control/src/np_gatt_server.c` (`np_gatt_on_write`), `np_session_stop.c`, `np_session_runner.c` (`np_runner_pause`); GitHub #1011) — the open stop, pause and panic writes told anyone in radio range about the wearer's session through their refusal codes.** A stop or a panic answered OK while a session ran and 0x80 otherwise, so a stranger who never paired learned whether the helmet was in use; a pause during ramp-up answered 0x82, and the hub ramps only with tDCS or cervical VNS in the protocol. **Closed by `REQ-FWHUB-81` (f) (NP-FW-HUB-001):** on a link that is not encrypted, a well-formed stop, pause or panic is acted on as before and answered OK whatever came of it; a malformed one is refused, the same in every state, and reaches no handler; an encrypted link gets the exact answer, so the apps (which act only on an encrypted link, and read state from `SESSION_PROGRESS` and `SESSION_HOLD`) lose nothing. Tested in `np_gatt_server_tests` (a mutant without the change fails three checks) and end to end through the twin (`fw-bridge.test.js`). **Not covered:** the answer's timing was not measured (the handlers only post an event, so it should not differ by state, but nothing shows it); whether these writes stay open at all is `OI-PRIV-24` (NP-PRIV-ANALYSIS-004) Q1, the principal's (`docs/human-input/oi-priv-24-resume-and-the-section-23-exception.md`).
