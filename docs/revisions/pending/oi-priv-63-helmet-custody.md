(1) **M1, checked.** `shdr_staging.bin` is one file with no record of which helmet staged it; the gate is checked for whichever helmet is connected when the signal arrives, and whatever is on disk is then sent, so helmet A's record can leave under helmet B's owner's consent and token. `FleetUploader.upload` reads the `@Volatile` `hubIdentifier` once for `isOpen` and again inside `deviceToken`. A revoke leaves the staged record, so a later grant sends records from before it. (2) **M4, checked.** `upgradeDeviceToken` silently replaces a stored hub token with a different one, which is what a factory reset or a change of owner produces, and that helmet's fleet consent, enrolment and epoch are kept; `clearForDeviceTransfer` has no caller (`OI-PRIV-20` (6)). (3) **L17, reported.** A user's migration clear removes every listed key, `np.warranty-owner.records` included (`clearAppHeldState` → `all_keys()`), so one user's transfer destroys a clinic's helmet records, against `REQ-SHDR-10`. **Closes when:** staging is per helmet (keyed by the salted hub hash, or checked against an identity the hub writes into the blob), one snapshot of the hub id serves the gate, the token and the read, and a revoke deletes that helmet's staged record; a different hub token over a stored one clears that helmet's consent, enrolment, epoch and staged record; and a user's clear leaves the warranty owner's records, each with a test. Related: `OI-PRIV-20`. **(1) and (2) fixed 2026-11-22; (3) checked and not fixed; the item stays open for (3).** **(1) Fixed (`REQ-SHDR-08` (e), (f)).** The hub firmware has no staging convention (nothing under `firmware/` writes or names the record), so the binding is the app's: `ShdrStaging` now takes a helmet key, and each record is a file of its own, `shdr_staging-<key>.bin`, where the key is `WarrantyOwnerStore`'s salted hash for the helmet (the salt is sealed, so a file name gives the Bluetooth address to no one without it; `FileShdrStaging` on the JVM hosts, `IosShdrStaging` on iOS, both refusing a key that is not 64 hex digits). A record is staged only while that helmet's owner consents (`WarrantyAnalyticsGate.stage`), read only for that helmet (`stagedRecord`), and `FleetUploader.uploadStaged(hub)` takes one reading of the helmet (the wiring passes `gattManager.hubIdentifier.value` once) for the gate, the token and the read, and deletes that helmet's record once the fleet service took it. `revoke` deletes the helmet's staged record. The unbound `shdr_staging.bin` an earlier version read names no helmet and is deleted unread when the staging is built. `upload(payload)` is now `internal`, for the transport tests only. **(2) Fixed (`REQ-SHDR-09` (d)).** `DeviceTokenStore` tells a hub-provisioned token from an interim one (`loadHubToken`, `saveHubToken`; the sealed table marks a hub token's line `hub:`). `upgradeDeviceToken` treats a hub token different from the hub token kept for that helmet as a change of custody and calls `WarrantyAnalyticsGate.endCustody`, which forgets the helmet's whole record (fleet consent, enrolment, epoch, programme) and its staged record, so the helmet reads as never asked and the new owner's first enrolment is epoch 1; the same token again, or a hub token over an interim one, changes nothing. The token is kept for the helmet the GATT link names when it arrives (`FleetUploadWiring.applyWarrantyToken(token, hub, uploader)`), not the uploader's copy, so a token is never kept, and a custody never ended, for the helmet before it. `CharacterisationEnrolmentGate.clearForDeviceTransfer` is removed: it had no caller and kept the fleet consent; `endCustody` is the one transfer path (`OI-PRIV-20` (6): the caller now exists; the enrolment screen still does not). **Limit:** a hub token kept by an earlier version has no mark and reads as interim, so the first different hub token after it is adopted without a custody change; no hub on silicon delivers the token yet (`OI-BLE-01`). **Tests** (`FleetUploaderTests`, `AnalyticsGateTests`): `aStagedRecordIsSentOnlyForTheHelmetThatStagedIt`, `oneReadingOfTheHelmetNamesTheConsentTheTokenAndTheRecord`, `nothingIsStagedForAHelmetWhoseOwnerHasNotConsented`, `theFileStagingKeepsOneFilePerHelmetKeyAndDropsTheUnboundFile` (08 (e)); `aRevokeDeletesTheHelmetsStagedRecordSoALaterGrantSendsNothingFromBeforeIt` (08 (f)); `aDifferentHubTokenOverAKeptOneEndsTheHelmetsCustody`, `theSealedStoreTellsAHubTokenFromAnInterimOne`, `theWiringKeepsAHubTokenForTheHelmetTheLinkNamesWhenItArrives` (09 (d)); `enrolmentDoesNotSurviveDeviceTransfer` now goes through `endCustody`. **Not compiled here:** the iOS staging (`IosHttpTransport.kt`, no Xcode) and the Android Application (no Android SDK). The SwiftUI app's own uploader still reads the one `shdr_staging.bin` and retires with that app (`OI-PRIV-20` (5)). **(3) Checked, not fixed: a design and a ruling, not a detail.** The finding is confirmed (`clearAppHeldState` → `all_keys()` lists `np.warranty-owner.records`), but taking the key out of the list would not keep the records: the clear's first step, `destroyEncryptionKey`, destroys the data key (and the presence gate's key) under which the records are sealed (`OI-PRIV-20` (4)), so what would remain is ciphertext that reads as absent, and the staged records are in the app folder that `overwriteAndDeleteFiles` wipes. Keeping them needs the owner's store to have a key of its own, which is `OI-PRIV-20` (1) and (4). It also meets `SWR-MG-09`, which requires the old phone to keep nothing that links it to the user or the helmet: an owner's records surviving a user's clear are such a link when the phone is the user's own, and are the clinic's data when the phone is the clinic's. **For the principal:** on a user's move off a phone, are the warranty owner's records kept (the phone is the owner's: a clinic install) or forgotten (the phone is the user's and leaves with them), and who says which? An erase (`SWR-MG-17`) forgets them either way.
