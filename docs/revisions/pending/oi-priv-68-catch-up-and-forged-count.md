(2) a device subscribes only while it is current for at least one of its users, one subscription per device, and the subscription carries no consent, user or study; (3) NeurOne publishes each request to all subscribed devices and filters nothing; (4) the device works out its current users and runs `admit()` for each, on the device only; (5) extracts go to NeurOne's research infrastructure as before, keyed to study ID only (`OI-PRIV-67`); (6) a request is published once and never re-published on a takeover; (7) current is per user and set by the person: a per-person current-device key (Ed25519, in the UHDR, carried by a restore, never rotated), a migration or restore that asks the research consents again and is not finished until they are answered, then a signed superseded notice (key id and a rising count) broadcast to subscribed devices, which an old device verifies against the key it holds; (8) the last device registered is current, and people with several devices must be told; (9) a restore finishes locally and queues its subscription and notice when offline; (10) a lost device that is never retired is a known edge; (11) push, accepted with its costs: the platform's push service learns the app receives these broadcasts, NeurOne holds a stable channel address per subscribed device (kept apart from the research store, SHDR and the warranty database), and a device with no push cannot be current for research; (12) the researcher portal shows the willing participant count only (`OI-PRIV-71`). **Earlier forms, superseded:** a per-person server record, a consent-bearing subscription, `poll`, a subscription secret and its verifier, and a from-scratch takeover; the trail is in `completed-decisions.md`. A from-scratch install holds no key, is a new person to the system, and needs no takeover. **Notice order and retention, RULED (the principal, 2026-11-21):** order is already the per-key count; what is missing is how a device that was offline catches up, and any retention time is a number with no derivation. Proposal: the server keeps **only the highest-count notice per key id and never expires one** (no number; a few dozen bytes per person who has ever moved, and a notice a higher count replaces is dropped); each notice also gets a server **sequence number**, a counter that names nothing; every `publish` carries the latest sequence; a device whose own cursor is behind it **fetches the notices after its cursor before it extracts anything**, which is the wake-and-fetch step already accepted for requests that do not fit a push, so there is no polling schedule; and a device that fetches nothing new extracts as before. Rejected (as ruled): a time limit (a number, and a device back after it extracts for someone it no longer serves); relying on the push service's own store-and-forward (its limits are not ours and not guaranteed). Costs: the fetch shows the server the device's address unless it goes through the relay (`OI-PRIV-69`); the list only grows; nothing stops junk notices for key ids that never existed from filling it (the server holds no key and cannot tell), which needs a cap that is a number. **Server store, OPEN (found 2026-11-25; brief `docs/human-input/oi-priv-68-forged-high-count.md`, DRAFT, recommends B):** "only the highest-count notice per key id" and "never drops a notice it holds" meet badly: the server cannot verify, every key id is broadcast to every subscribed device, so anyone who has seen one can send a junk notice for it with a top count, the server keeps the junk and drops the real notice, and every later real move by that person is dropped too, so their old device is never retired. Options: keep every notice per key id (A), send the public key with each notice so the server verifies before storing, with no new record (B), or accept the gap (C). `NP-SW-PORTAL-API-001` §6a now says nothing about which notices per key id the server keeps until it is ruled. **Device catch-up, BUILT 2026-11-25** as `supersededCatchUp` and `may_extract` in `common/npps-core/src/current_device.rs` (`SWR-MG-35`, six tests in `tests/current_device.rs`): the cursor moves to the highest sequence above it and never back, junk and malformed notices move it and retire no one, a person is retired only by a verified higher count, which the device then records, and the device may extract only once its cursor has reached the latest; it works whichever option the server-store question takes. No host calls it and no fetch exists. **Not built, and open:** ~~whether `supersede` and the fetch go through the relay~~ ruled with `OI-PRIV-69`: they do; **junk notices, RULED (the principal, 2026-11-21):** a notice that does not verify can retire no one, because every device checks the signature against a key it holds, so flooding costs the server storage and every device bandwidth (each fetches what follows its cursor) and breaks nothing else. The server holds no key and cannot tell a junk notice from a real one, and giving it keys would bring back a per-person record. As ruled: (1) the relay, which already sees each sender's address and nothing else, **limits how many `supersede` calls one address makes** (no new party learns anything; the figures are operational settings, each a row for `docs/status/unjustified-choices.md` when set); (2) the server **refuses new notices when its store reaches a generous total, and never drops one it holds**, so the failure is that a real move cannot publish its notice and the old device stays current for a while, never that a real notice is lost; (3) a device **fetches in pages** so one flooded stretch does not arrive in one response. Rejected: dropping the oldest notices when full (it would retire a real notice, which the "never expires" ruling forbids); a short tag of the key id to fetch only matching notices (it tells the server a device holds a key whose id begins that way, and the tag length is a number with no derivation); proof of work (a number, and it taxes real phones). **Not built, and open:** the figures in (1) and (2), set by whoever runs the service; **push size, RULED option (1) (the principal, 2026-11-21): always wake-and-fetch; FCM 4096 bytes for notification and data messages, on Firebase's "message types" page; WNS raw notification smaller than 5 KB, on Microsoft Learn's raw notification overview; Web Push 4096 bytes in practice, with RFC 8030's own wording not yet read. **Checked against the sources 2026-11-22 and again 2026-11-25 by opening the pages:** WNS raw notification matches ("smaller than 5 KB", Microsoft Learn raw notification overview); The smallest is 4096 bytes, and a signed descriptor sent as text in a payload grows by a third (base64) and by the platform's envelope, so what fits is a function of the smallest limit minus the envelope, never a figure stated beside it (`CLAUDE.md` §18), and a descriptor with a long title or many elements will not fit. Options considered: (1) **always wake-and-fetch**: the push carries only the latest publish and notice sequence numbers, and the device fetches the request through the relay. One path, since a device behind on notices must fetch anyway; the push service sees that a request was published and nothing about which one; the cost is that every subscribed device fetches at once on each publish. (2) **Carry the descriptor when it fits, fetch when it does not**: fewer fetches, two paths, and the push service and its logs hold the descriptor's title and elements.
