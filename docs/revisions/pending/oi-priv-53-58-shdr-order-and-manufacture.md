text: - [ ] **`OI-PRIV-76` (raised 2026-11-22, from closing `OI-PRIV-53`; `REQ-SHDR-11` (c); `NP-INFRA-001` §3.4; `ci/shdr/shdr_fleet_schema.sql`) — the fleet database still records insert order in every row's `xmin` and `ctid`.** Schema Rev G removed the explicit sequences, but PostgreSQL gives every row a transaction ID (`xmin`, assigned in commit order across the whole database) and a physical position (`ctid`, roughly insert order until rows are rewritten), and anyone who can run SQL on the fleet database reads both. So the same thing `OI-PRIV-53` closed for the `id` column still holds one level down: within a month, `xmin` orders every device's dockings and groups one docking's rows in every table, and an outside time anchor (ingest logs, WAL or backup times) turns the order into roughly day-level time. Freezing keeps the `xmin` value, and `VACUUM FULL` or `CLUSTER` keep `xmin` while rewriting `ctid`. Nothing in the repository can fix this, because the ingest service does not exist yet (`OI-FLEET-01` (e)). **The design to build with it:** the ingest stages what it receives and writes it to the SHDR tables in batches, each in one transaction and in random order (`INSERT … SELECT … ORDER BY random()`), so the rows of a batch share one `xmin` and their physical order carries nothing; the batch is at least a month, or a count large enough that one batch spans many devices; the staging area holds the record only until the batch is written and keeps it nowhere else; and the database's own logs keep no statement text (`log_statement = none`). Read access to the fleet database is limited to the people who run it, with an audit trail. **Closes when:** the ingest is built that way, shown on a test database (`xmin` and `ctid` order within a batch say nothing about which device docked first), and `NP-INFRA-001` §3.4 states the batching as the deployment rule. Owner: Software.
