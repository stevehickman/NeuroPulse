text: - [ ] **`OI-PRIV-78` (raised 2026-11-25, `NP-PRIV-ANALYSIS-006` F-13, checked against `main`; `CLAUDE.md` §5.1; `SWR-MG-17`, `SWR-MG-30` (d), `REQ-SW03-19` (d); `app/NeurOneUI/shared/src/commonMain/kotlin/life/neurone/shared/PlatformServices.kt` `eraseLocalData`, `endRunAfterErase`; `EraseDeviceModel.kt`; `IosSecretKeyStore.kt`, `IosGatedSecretKeyStore.kt`; GitHub #1060) — phones have no in-app erase, and the premise that a phone's data goes with the app is false.** `SWR-MG-17` offers "erase the data on this computer" on the desktop apps only: "Phones are not offered it (a phone's data goes with the app, and the device-replacement clear is there)". `PlatformServices` leaves `eraseLocalData` and `endRunAfterErase` null on phones, so `SettingsScreen` shows no erase there. Removing the app does not do what the in-app erase does. (1) **iOS Keychain items survive an uninstall** (widely reported platform behaviour that Apple does not document; to be confirmed on the `OI-PRES-07` device run). On the shared iOS host that ships, the Keychain holds the data key (`life.neurone.data-key`, `AfterFirstUnlockThisDeviceOnly`) and, once the gate is offered, the gated UHDR key (`life.neurone.uhdr-key`). The sealed values themselves (warranty tokens, the analytics ID and its queue, consents) are in `NSUserDefaults` and `Documents/`, which go with the app, so the key left behind protects nothing that remains; it is still a key that protected erased data, which `OI-PRES-10` rules an erase does not leave, and a reinstall finds it. The finding's list of Keychain items (UHDR seed, warranty tokens, signing key) was the SwiftUI app's, deleted by #946. (2) **An analytics ID the person opted into is never sent to the erasure relay** when the app is removed: the in-app erase forgets the ID, queues it and drains the queue before the wipe (`REQ-SW03-19` (d)), and an uninstall runs nothing, so the vendor keeps those events until its 30-day retention (`OI-ANALYTICS-01` (3)). This holds on Android as well as iOS. (3) **A cloud grant is not revoked**: the erase revokes Google and Dropbox grants at the provider (`SWR-MG-30` (d)); an uninstall leaves the refresh token valid there. Same on both phones. On Android the rest of the premise holds as far as the code shows (`allowBackup="false"` and data-extraction rules; Keystore keys are expected to go with the app, unconfirmed until the `OI-PRES-06` device run). **Options** (not exclusive): **A.** Offer `EraseDeviceModel` on phones, which brings the queue drain (`REQ-SW03-19` (d)), the cloud revocation (`SWR-MG-30` (d)) and, on iOS, the gated key's deletion (#935, fixed by #944) with it. A phone cannot end its own run (iOS apps are not to quit themselves), so the host needs another way to drop the old in-memory state: rebuild the app's services in place, as the browser reloads. **B.** On iOS, purge the Keychain items on the first launch after a reinstall: a marker kept in the app container is absent while a Keychain item exists, so the items are deleted before anything opens. It removes the residue of (1) only at a reinstall, and does nothing for (2) or (3). **C.** Drain the erasure queue and revoke cloud grants at erase (both come with A), and, for the uninstall that cannot run code, tell the person on the analytics and cloud screens to turn them off before removing the app, accepting the 30-day retention for the rest. **Recommended:** A on both phones, B on iOS, and C's notice. **Needs a principal ruling:** `SWR-MG-17` decided that phones are not offered the erase; the brief is `docs/human-input/oi-priv-78-phone-erase.md`. Related: `OI-PRES-07`, `OI-PRES-10` (closed), #936 (open: a gated install whose Keychain item is gone; after a reinstall that state is the normal empty one), `OI-ANALYTICS-01`, `OI-EDF-01` (a device backup made before an uninstall keeps what it did not exclude). **Closes when** the principal has ruled, `SWR-MG-17` says which hosts offer the erase, and what is chosen is built with its tests.

text: - [ ] **`OI-CONSENT-08`: review all clinician tiers and what each one contains (raised 2026-10-07, OPEN — decision owner: principal, with clinical advisor input)** — the tier table (`app/NeurOneShared/Resources/clinician-tiers.json`) and the element table (`app/NeurOneShared/Resources/uhdr-elements.json`) are the single sources for `ClinicianUseCaseTier` and `UHDRElement` on both apps. Neither has ever been reviewed as a whole: which UHDR elements each tier (Monitor, Assess, Full Clinical) reaches, each element's `minimumTier`, the tier ranks, and the $49/$149/$299 per patient and $599 per study prices (`CLAUDE.md` §6.1). **What prompted it:** `EYE_STATE_LOGS` had `minimumTier` Full Clinical but was in no tier's set, so no clinician grant could ever reach it. Nothing in the history says that was a decision, and the existing ISC-137 test only checks that no tier holds an element below its minimum, not that every element is reachable. It was added to Full Clinical on 2026-10-07 at the principal's direction, which makes Full Clinical 11 elements and every element reachable. **The review should settle:** (1) whether each element sits in the right tier, with sensitivity as the test (eye state is IR-derived and near-physiological; HRV and PPG are physiological), not only convenience; (2) whether the tier sets should stay derived from `minimumTier` (the generator does this today), so the two cannot disagree again; (3) whether the elements a use case needs (`clinician-use-cases.json`) match the tier that offers it, since no library use case names eye state; (4) whether any element should be reachable only through a Research study descriptor (§6.3); (5) whether the prices, which have no derivation, are decided; (6) **(added 2026-11-25, `NP-PRIV-ANALYSIS-006` F-08) whether each use case names only the elements it needs.** `CLAUDE.md` §6.1 and `REQ-CONSENT-15` (a) say a grant reaches the *minimum* UHDR elements for the chosen use cases, and `ConsentEngine.minimumNecessaryElements` derives exactly the union of their `requiredElements`; but `clinician-use-cases.json` gives each use case its whole tier's set, so the derivation is minimal over a table that is not. `hrv_outcomes` requires `EEG_WAVEFORMS`, `NEUROFEEDBACK_SCORES`, `PBM_DOSE_LOGS` and `PPG_OPTICAL_SIGNAL` besides `HRV_TIME_SERIES`, so an HRV grant also hands over raw brain activity and the raw optical pulse signal; `eeg_review` requires `PBM_DOSE_LOGS`. Point (3) asks whether a use case's elements fit its tier, which this table passes; (6) asks whether they are its minimum, which it does not. **Proposed, for the principal and the clinical adviser to confirm or change (nothing is edited until they do):** `adherence_monitoring`: `SESSION_TIMESTAMPS`, `SESSION_DURATION` (`PROTOCOL_PARAMETERS` only if adherence means adherence to a prescribed protocol, which is a clinical question); `eeg_review`: `EEG_WAVEFORMS`, `SESSION_TIMESTAMPS`, `SESSION_DURATION`; `hrv_outcomes`: `HRV_TIME_SERIES`, `SESSION_TIMESTAMPS`, `SESSION_DURATION`. Each element dropped becomes its own use case if a clinician needs it (for example neurofeedback progress, PBM dose review, closed-loop review, outcome tracking, eye state), so it is chosen knowingly and the user is told of it; whether raw `PPG_OPTICAL_SIGNAL` should be reachable by any use case, when HRV is derived from it, is part of the ruling. The table, the reasons per element and the question are in `docs/human-input/oi-consent-08-clinician-tiers.md` Q6. The use-case sets have no derivation (`UC-212`). Any change to a tier set changes what a clinician grant reaches and so what a user is told a clinician can learn (§6.1), which is why the review precedes further edits. Related: `OI-CONSENT-04`, `UC-069` in `docs/status/unjustified-choices.md`. **Closes when** the principal has signed off the two tables and the use-case library (`clinician-use-cases.json`, for (6)) and the outcome is recorded in `docs/status/completed-decisions.md`.
