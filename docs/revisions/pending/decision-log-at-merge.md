Now each goes in the PR's revision fragment (`docs/revisions/pending/<slug>.md`): the decision-log entry in its `## LOG` section, the history entry in its `## CLAUDE.md` section (whose first paragraph opens with the revision and date as tokens), and the open-items edit as `## OPEN` hunks, which `bun scripts/assign-revisions.ts --convert-open` writes from an ordinary edit of the page. A hunk is found by the text of the lines it replaces, so an edit to the next item does not disturb it. The Document Map names all three. `check-revision-fragments` fails a PR that adds a log entry by hand (rule K), that changes this file without a `## CLAUDE.md` section or numbers it by hand (L), or that edits the open-items page directly (M), and dry-runs every pending `## OPEN` edit (N), so two PRs that change the same item fail on the second PR, not on `main`. In mode `hand` authors do all of it by hand as before.
text: **Why.** The log is append-only with every entry at its end, this history is newest-first with every entry at the top of "Current revision", and the open-items page has one item per line, edited in place. Git refuses two branches' changes to the same or adjacent lines, so any two PRs that logged a decision, changed this file, or changed neighbouring open items conflicted, and the second to merge resolved it by hand; two that changed this file also took the same revision number. That is the collision that moved revision numbers to merge time on 2026-11-02. With `main` now requiring a branch to be up to date before it merges (`OI-SWCI-53`), each merge sent every other such PR back to resolve it.
text: **What it leaves.** Prose and tables in other documents still merge as git merges them. This revision is the first numbered by the workflow, and this fragment's own edit of the open-items page header the first applied that way. The §1 to §6 and §16 to §23 numbering and every subsection number are unchanged.
