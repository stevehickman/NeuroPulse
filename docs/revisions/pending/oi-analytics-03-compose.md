Its own `docker-compose.base.yml` and `docker-compose.hobby.yml` on `master`, read that day, define 63 services: separate Rust services for capture, feature flags and the personhog family, Redpanda in place of Kafka, Valkey, SeaweedFS, Temporal and Elasticsearch. Almost every image floats on `:master`, but ClickHouse is pinned exactly, to PostHog's own build `ghcr.io/posthog/clickhouse-posthog:26.9.5.2-posthog-…` (ClickHouse 26.9). `infra/posthog/docker-compose.yml` has about ten services: the Django web server with the plugin server, Bitnami Kafka 2.8, and `clickhouse-server:23.12`. It almost certainly cannot run a current PostHog image. `.env.example` asks for a `POSTHOG_VERSION` release tag such as `release-1.43.0`, and no such tags are published now. Every privacy control in `infra/posthog` was written against the old layout and is unverified against the new one: `clickhouse/np-privacy.xml`, `apply_event_retention.py` (the TTL on `posthog.sharded_events`), `apply_project_settings.py`, the erasure relay's table name and grants (`OI-PRIV-48`), Caddy's routing and log filters, and the Docker log limits (`OI-PRIV-46`). `OI-ANALYTICS-01` (2), `OI-ANALYTICS-02` and `OI-PRIV-56` all assume a pinned PostHog version, so each now waits on this item. **The plan (agreed by the principal 2026-11-26).** (1) Rebuild `infra/posthog` from PostHog's current hobby compose. (2) **Pin by commit:** pin PostHog to one commit's images, and take ClickHouse, and every other image whose version PostHog sets, from that same commit's compose file, never chosen on its own, because PostHog's queries and migrations target that ClickHouse. Upgrading means deliberately moving the whole stack to a newer commit and re-running the retention, settings and erasure checks: an upgrade that recreates the events table drops the 30-day TTL, and one that renames it leaves the erasure relay deleting nothing, both silently. (3) Add a minimum-version check (`SELECT version()`) as a guard on top of the pin, not in place of it. (4) Re-check every control listed above on the new layout, in the procedure of `NP-MAN-OPS-001` §4. (5) Once ClickHouse is 24.10 or later (PostHog's is 26.9), make the narrow design the erasure relay's: a parameterized view with `SQL SECURITY DEFINER` that answers only "which of these IDs still have events", in place of `np_erase` reading the whole `distinct_id` column (`OI-PRIV-48`). ClickHouse added `SQL SECURITY DEFINER` in 24.2 and extended it to parameterized views in 24.10 (changelog, PR #69984); before 24.2 a view could be read only by a user who could also read the table behind it. **Closes when:** the stack runs a pinned PostHog commit with its own ClickHouse, the pin-by-commit rule and the upgrade procedure are written in `NP-ANALYTICS-001`, every listed control has been re-checked on it, and `.env.example` no longer asks for a release tag. **Pin mechanism decided 2026-11-27 (the principal, option A of `docs/human-input/oi-analytics-03-pin-mechanism.md`).** PostHog rebuilds each image it builds only when that service's code changes, so no commit has a full set of images: the compose files come from the commit, and each PostHog-built image is pinned by digest to the build its floating tag named, whose `org.opencontainers.image.revision` must be the commit or an ancestor. **Part (a) built 2026-11-27 (`REQ-SW03-41`;
