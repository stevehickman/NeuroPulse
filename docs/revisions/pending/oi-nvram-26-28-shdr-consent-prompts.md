text: - [ ] **`OI-NVRAM-28` (raised 2026-11-26, from the principal's refinement of `OI-NVRAM-25` (b) and the timing-gap answer; `NP-FW-NVRAM-001` §8.5, D-39, §13; `NP-MOD-ID-001` §7.3, §7.4, §7.5; `docs/reference/data-architecture-detail.md` `REQ-SHDR-12`; `OI-NVRAM-26`, `OI-PRIV-20`) — link general SHDR consent's ongoing content to the §7.4 review gate, and build the post-analysis notice.** The principal: general consent is not time-bounded and covers the content predictive maintenance needs on an ongoing basis, which is known only once the characterisation data is analysed; it may be as much as characterisation used, or less. (1) **The content set:** when the `NP-MOD-ID-001` §7.4 gate rules, record which fields general consent then covers (everything characterisation collected, the baseline only, or between), as a versioned set the device and the app can name; until it rules, the baseline. A helmet sends no field above the set its owner agreed to, and content the gate adds waits for the owner's answer to prompt (2). (2) **The notice, ruled by the principal (2026-11-26):** "Analysis done would be broadcast through an app update mechanism to all warranty owners." It is a broadcast, the same to every warranty owner, carrying the general-consent content set the gate fixed; it is not targeted and needs no per-owner channel (the pattern of `CLAUDE.md` §6.3, where NeurOne publishes the same thing to every device and filters nothing). Each owner's app then shows prompt (2) (`OI-NVRAM-26`). **Left to build, not designed here:** how the content set ships in an app update, and how the app knows to show prompt (2) once. (3) The fleet schema and `ci/test_shdr_schema.py` follow the set, and `DOSE-01` is never relaxed. **Closes when** the set is recorded and enforced on the helmet and in the schema, and the app update that carries it is built and shown once per owner. Owner: Firmware and the Privacy Lead for (1) and (3); the owner of the warranty owner's page (`OI-PRIV-20`) for (2), with `OI-NVRAM-26`. **(2) built in the app 2026-11-26** (`NP-FW-NVRAM-001` Rev {NP-FW-NVRAM-001 to}, §13). The content set rides in the app build (`GeneralShdrContent.history`, oldest first, the last in force; the baseline alone until the gate rules), so every install of a release carries the same set. Nothing is fetched, no server learns who received it, and nothing names an owner. A set the gate fixes ships as a new entry with the words for each item it adds (`GENERAL_CONSENT_ITEM_NAMES`, `locales/<bcp47>.json`). A test holds the shipped history to that table, and a history that is not well formed shows nothing and changes nothing. Prompt (2) shows once per owner and helmet (`contentAsked`). The owner's agreed version is recorded (`contentLevel`) and rises only by their yes (`REQ-SHDR-12` (d)). **Still open:** (1) and (3) on the helmet and in the schema. The app's uploader sends the hub's record as delivered (`REQ-SHDR-03` (c)) and cannot withhold a field, so the device must know the set and send no field above the owner's version. How the device learns the version, and whether the set needs a signature the device can check apart from the app's, are not designed. If the principal meant a separately signed content file rather than the app build, (2) changes too (`docs/human-input/oi-nvram-26-28-general-consent-prompts.md` §2).
