---

> **Scope in one paragraph.** The helmet simulator (`NP-SIM-001`) draws a helmet and replays a protocol
> against a model written for the purpose. This document designs the next step: **the simulator runs the
> real hub firmware**, with each physical module an object that holds its own state, draws itself, and
> can be told what to answer. The purpose is **whole-system effects**: a developer changes one module's
> behaviour and sees what the rest of the system does about it, where a unit test calls one function in
> isolation and cannot. **A second aim:** to the degree possible the same code is the basis
> of a bench test apparatus (§11). **§12 records the first build, the PBM spike.** §8 is the
> build order and §9 the decisions needed first.

## 1. What exists today

Read from the tree on 2026-11-01. Nothing in this section is a proposal.

| Question | Answer | Where |
|---|---|---|
| Does the simulator run helmet code? | **No.** `SessionEngine` is a JavaScript model that reads a parsed protocol and produces plausible numbers. Its header says all physics is fake, and its dose accumulation line is multiplied by zero. The only shared code is the Rust NPPS parser, run as WebAssembly. Nothing under `simulator/` names `firmware/`. | `simulator/js/session.js` |
| Is a module an object with its own state? | **No.** `HelmetModel` keeps per-zone configuration and recomputes each socket from the winning zone. A socket is a render slot. Session state is one global snapshot keyed by modality. | `simulator/js/helmet.js` |
| Does a module draw itself? | **No.** `HelmetModel` and the app's render loop draw everything. | `simulator/js/helmet.js`, `app.js` |
| Can a module be told what to answer? | **No.** The device API accepts `SESSION_START`, `SESSION_PAUSE`, `SESSION_STOP`, `ZONE_CONFIG` and `ACCESSORY_CONFIG`, and sends `TELEMETRY`, `FAULT` and `SESSION_COMPLETE`. `sendFault()` exists and nothing calls it. | `simulator/js/api.js` |
| Is there a firmware seam to attach to? | **Yes, and it is already single-sourced.** `np_sw02_platform_hal.h` plus eleven module headers declare the whole hardware-facing contract, `NP_SW02_PLATFORM_SYMBOL_COUNT` = 119. | `firmware/platform/include/` |
| What does `firmware/platform/` do with that seam? | **Every symbol is a trap that halts.** It is cross-compile only (`if(NOT CMAKE_CROSSCOMPILING) return()`). Its header argues that a stub answering plausibly is how an interlock is silently defeated. | `firmware/platform/` |
| Is there a plausible-answer double? | **Yes, for PBM only, host-test only, global and not scriptable.** It answers ACK on every probe and returns nominal photodiode counts. | `firmware/pbm/src/np_pbm_hal.c` |

## 2. Feasibility, measured

The design depends on two facts that could have been false. Both were tested on 2026-11-01 in a scratch
build outside the tree (`cmake -DNP_BUILD_TESTS=ON`, gcc 13 / clang 18, Linux x86-64).

| Finding | Result |
|---|---|
| Does FreeRTOS run on the host? | **Yes.** `vendor/freertos/portable/ThirdParty/GCC/Posix` is vendored and `FreeRTOSConfig.h` has an `NP_FREERTOS_POSIX_HOST` branch. The full host suite builds and **all 63 tests pass**, including `np_freertos_smoke_tests`, which runs the real scheduler. |
| Does the hub compile on the host? | **Yes.** Every source in `hub_control/`, `pbm/`, `zone_announce/`, `cervical_vns/`, `shdr/`, `hrv_biofeedback/` and `sloreta_hdtdcs/` compiled with the POSIX port and zero failures, including `np_hub_control_main.c` (five tasks and `vTaskStartScheduler`) and every module under `hub_control/modules/`. `np_pbm_hal.c` was excluded, because the simulator's platform layer replaces it. |
| How much is unresolved at link? | **116 symbols**, of which about **94 are platform seams** and the rest are libraries already in the tree: `lfs_*` (vendored littlefs), `np_ed25519_verify` and `np_sha256` (`firmware/crypto`), `np_factory_reset_boot_check`, `np_za_platform_*`. This is a scan of undefined symbols, not a link. |
| Can the firmware run in the browser as WebAssembly? | **Not without new work, and not recommended.** The POSIX port is built on `pthread_create`, `pthread_kill`, `sigwait`, `sigaction` and `pthread_cancel`. Those need SharedArrayBuffer plus special HTTP headers in a browser, and signals do not exist there. No FreeRTOS WebAssembly port exists, so it would be a custom port (Emscripten fibers or Asyncify), which is a new kernel to qualify. Emscripten (`emcc`) is not installed here, and clang has no C sysroot for `wasm32`. |
| Does the safety MCU run on the host? | **Yes.** All 12 sources in `firmware/safety_mcu/src/` compile with gcc and no warnings; 11 as they are and `np_gpio_mgr.c` with the force-included `tests/np_gpio_mgr_test_ports.h` its own host test already uses. Linked against a scratch HAL that defines the 41 `np_hal_*` functions of `np_safety_hal.h` plus `firmware/crypto`, the real `main()` ran its init sequence and its `for(;;)` loop with no source change. At boot all ten enable lines went to 1 (disabled). With no heartbeat it granted nothing. Valid heartbeats requesting the cranial enable were answered. What was **not** exercised: the signature path, the thermal, charge and cardiac interlocks, the tier gate, and the watchdog cutoff after a running grant. The loop is a busy-poll, so the host HAL needs a pacing point. |
| Two small defects the host build exposed | `xPortIsInsideInterrupt` is missing from the POSIX port (`np_hub_control_main.c:125` calls it). `portMAX_DELAY` is 64-bit in the POSIX port and the tick type is 32-bit, so the constant truncates; it still works as a very long wait. Both are `OI-SIMFW-03`. |

**Conclusion.** The firmware, hub and safety MCU, can run natively on the host with its real tasks. It
cannot run in the browser without a custom kernel port. The design in §3 follows from that.

## 3. Architecture

```
 ┌──────────────────────────── browser (simulator/) ───────────────────────────┐
 │  SimModule instances ── state · render() · inspector · fault controls        │
 │       ▲  ▼  MODULE_LIST / MODULE_SET / MODULE_FAIL        (WebSocket)        │
 └───────┼──┼──────────────────────────────────────────────────────────────────┘
         │  │            ws://localhost:9000  (simulator/server/index.js)
 ┌───────┴──┴───────────────────────────────────────────────────────────────────┐
 │  bridge (Node) ── starts and supervises the firmware process, relays messages │
 └───────┬──────────────────────────────────────────────────────────────────────┘
         │ local socket
 ┌───────┴──────────────────── firmware process (native) ───────────────────────┐
 │  unmodified hub_control / pbm / zone_announce / cervical_vns / … sources      │
 │  FreeRTOS POSIX port (real tasks, real heartbeat)                             │
 │  sim platform layer: defines every seam symbol, routes by (kind, index)       │
 │  module mirror: one small state record per module, synchronous to read        │
 │  file-backed block device for littlefs · firmware/crypto for signatures       │
 └───────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 The firmware process

- **Built from the firmware's own sources, unmodified.** The simulator links the same `.c` files the
  device image does, with the sim platform layer in place of `firmware/platform/`. **No
  `#ifdef SIM` appears in a firmware source file** (`REQ-SIMFW-03`). A simulator that runs
  different code from the device is the thing this design exists to avoid.
- **Real tasks, real timing.** `task_safety_heartbeat`, `task_hub_control`, `task_protocol_rx`,
  `task_telemetry` and `task_module_detect` run under the POSIX port. The interactions between them
  are what a unit test cannot show.
- **Timing is indicative, not evidence.** The POSIX port schedules on a general-purpose OS, so a
  200 ms heartbeat or a 1.5 s watchdog observed here says nothing about the device (`REQ-SIMFW-06`).
- **The time model is decided and not built (`OI-SIMFW-04`, the principal, 2026-11-11):** one virtual timeline with a clock domain
  for the hub, for the safety MCU's SYSCLK and for its independent watchdog (`REQ-SIMFW-22`). The two bullets above describe
  the design as first written, with real tasks under the POSIX port on the host's clock; neither that nor the decided domains
  is what runs. What runs (§31) is the hub's five tasks on the twin's own virtual-time scheduler and the one virtual counter the
  safety MCU model reads (§22, §30).

### 3.2 The sim platform layer (`firmware/platform_sim/`, proposed)

- **Defines every seam symbol once.** The set is parsed out of the headers at build time, as
  `scripts/check-platform-seam-decls.ts` already does, and never restated in a second list.
- **Routes by `(kind, index)`.** Each seam call becomes `sim_bus(kind, index, op, args)`:
  `np_mod_pbm_hal_socket_ntc_read(socket_id)` goes to the module at that socket;
  `np_mod_visual_hal_goggle_seated()` goes to the goggle singleton. A seam with no route fails the
  build (`REQ-SIMFW-02`), mirroring the census at `firmware/cmake/np_platform_census.cmake`.
- **Answers from the module first.** If the module has an injected response for that op, that wins.
  Otherwise the module's default model answers.
- **Cannot reach a device image** (`REQ-SIMFW-01`). The directory builds only under the host
  toolchain, as `firmware/platform/` builds only under the cross toolchain, and a CI check fails if
  an ARM target links it.

### 3.3 `SimModule`

One instance per physical thing. Addressing is the firmware's own: **socket** (PBM base and smart
tiles, 0-based index space), **slot** (accessories), **side** and **pair** (stim and VNS).

| Field | Meaning |
|---|---|
| `id`, `kind`, `address` | identity; `kind` is one of `pbm_base`, `pbm_smart`, `eeg`, `audio`, `visual`, `vns`, `intranasal`, `stim_pair`, `cvns`, `tms` |
| `state` | what the module holds: commanded output, temperature, impedance, seated, present, faulted |
| `handle(op, args)` | returns the HAL result for a firmware call; default model unless overridden |
| `setResponse(op, code, {times, until})` | the next calls to `op` return `code`, a `np_hub_status_t` |
| `setReading(op, value)` | pins a read, for example NTC at 71 °C or an impedance |
| `setPresent(bool)` | detection reports `NP_HUB_ERR_NOT_PRESENT` when false |
| `setSeated(bool)` | fires the Hall interrupt callback when it goes false |
| `render(dt)` | the module draws itself: glow, temperature tint, fault colour |

Status codes are generated from `firmware/hub_control/include/np_hub_types.h` into the browser by the
mechanism that generates `sockets.generated.js` today, so there is one list (`REQ-SIMFW-05`).

### 3.4 Authority and the safety MCU

**A module draws as driven only if the firmware commanded it and the safety MCU's enable line for it is
asserted** (`REQ-SIMFW-07`). Without that, the simulator would show a tile lit that the real helmet
would have cut, and the one property CLAUDE.md §4.2 rests on (the safety MCU owns every enable) would be
invisible. This requires the safety MCU firmware (`firmware/safety_mcu`, STM32G071, bare-metal) to run
in the loop. **It can** (§2, `OI-SIMFW-01` closed): the safety MCU is a separate host process or
thread with its own seam, the 40 `np_hal_*` functions of `np_safety_hal.h` (an earlier revision counted 41; the header declares 40, §22), of which the SPI functions
face the hub's `np_safety_hal_spi_transfer`. As built (§22) it is a thread and a set of `safety_*` harness commands, not a `SimModule` kind: that is where a developer forces a
thermal reading, a bad signature or a missing heartbeat. Until it is wired in,
the simulator tests hub behaviour only and must say so on screen.

### 3.5 Bridge protocol

New messages beside the existing ones; the existing ones are unchanged.

| Message | Direction | Carries |
|---|---|---|
| `MODULE_LIST` | firmware to browser | every module: id, kind, address, state |
| `MODULE_STATE` | firmware to browser | one module's changed state, including the last commanded value and the enable it holds |
| `MODULE_SET` | browser to firmware | patch to one module's state |
| `MODULE_FAIL` | browser to firmware | `{id, op, code, times}` — an injected response |
| `MODULE_CLEAR` | browser to firmware | removes one module's injected responses |
| `FW_LOG` | firmware to browser | the hub's own log lines, so a developer sees cause and effect together |

The browser's inspector (click a module in the 3D view) sends these. A headless test sends the same
messages, which is how the simulator's own tests drive it.

## 4. What this lets a developer see

Each is an effect that crosses a module boundary, which is the case unit tests miss.

| A developer changes… | …and sees |
|---|---|
| A socket's `pwm_set` to fail with `MOD_FAULT` | the dispatch rolls back every socket the command started, the cranial enable drops only when none remain, and the runner's session record shows what was delivered |
| A tile's NTC reading to 71 °C | the thermal path throttles or cuts, the other tiles continue, the app is told |
| Goggle seated to false mid-session | the Hall interrupt fires, visual stops within its limit, and PBM and audio continue |
| A module removed mid-session | `task_module_detect` notices, the registry deregisters, the runner's reaction |
| The heartbeat task delayed | the safety MCU's watchdog behaviour on the cut (needs `OI-SIMFW-01`) |
| A new PBM mask in a protocol | the placement check, the power governor refusal (the production governor refuses every load, `np_socket_dispatch.h`), and where the refusal surfaces |

| **`REQ-SIMFW-16`** | **The page has a fault panel: every fault the system is built to detect that the page can cause is a button, and each is an input to the firmware, never a verdict.** (a) Each fault is a list of `FW_COMMAND`s the bridge validates (`REQ-SIMFW-15` (a)); a fault that stays until undone has a Clear that restores only what it set. (d) A fault the system should detect that the page cannot cause is listed on the panel with the reason, so a missing button is not read as a pass. | (a) A button the bridge refuses, or a Clear that undoes more than its fault. (b) The simulator hides or invents a recovery, so a run no longer shows what the firmware does. (c) A real outage leaves the simulated MCU's view of the hub unchanged. (d) An absent detector reads as a passing one. | CLAUDE.md §4.2; `REQ-SIMFW-06`, `REQ-SIMFW-07`, `REQ-SIMFW-15`; `OI-SIMFW-27`, `OI-SIMFW-41` |
| **`REQ-SIMFW-17`** | **The app's protocol reaches the twin as the device's own framed bytes, and the hub's own code takes it in.** (a) The bridge relays an upload as bytes: validated hex of the framed stream (a 4-byte little-endian length, then the blob), no command invented and no byte parsed in the bridge. (b) The twin gives those bytes to the hub's own transport (`np_transport_feed`) and takes the blob out as the hub's protocol task does (`np_hal_proto_queue_receive`), so a blob split over any number of writes is reassembled by the device's code, a bad length prefix is refused by it, and a second blob is refused until the first is taken. (c) The app receives the hub's own upload-check frame (`np_upload_check.c`: the SHA-256 of the bytes as they arrived, then the verdict), the verdict is the hub's own `np_runner_load` (the boot admission, the session lease, `np_protocol_verify_and_parse` with the device-serial replay guard, then the tier, hardware-version, layout, address and photic checks, in the runner's order), and the twin says whether a session started: without `hub_boot` none did, because no task runs the runner; after it the hub's own tasks run it (§31, `REQ-SIMFW-23`). (d) The signature is checked against a TEST protocol key, and the signing stand-in that uses it is labelled a simulator test aid. (e) The device-serial replay guard is live against a TEST device serial, so a protocol for another serial is refused as `NP_HUB_ERR_WRONG_DEVICE`; the boot admission is the firmware's own flag, so a boot that did not admit sessions refuses every protocol as `NP_HUB_ERR_BOOT_REFUSED`; and a protocol loaded holds the session lease, so a second is refused while it is held. | (a) A client puts a string into the command line of a process that runs the hub. (b) The twin reassembles or refuses an upload differently from the device, so an app that works against it fails on the helmet. (c) The app trusts a hash or a verdict the hub did not give, or a session appears to start that did not. (d) A TEST signature is taken for a production one. (e) A protocol meant for one helmet runs on another, or the app is told a protocol was loaded on a boot that refused sessions, or two sessions' descriptors are held at once. | `docs/np_sim_fw_001.md` §25 (the twin speaks the device's protocol); `REQ-SIMFW-06`, `REQ-SIMFW-08` |

## 6. Placement and governance

- **`firmware/platform_sim/`** holds the sim platform layer. It is firmware-adjacent and builds with the
  firmware, so it belongs there and not under `simulator/`. Neither side names a path under `app/`
  (CLAUDE.md §20, `scripts/check-shared-placement.ts`). The bridge and `SimModule` live in `simulator/`.
- **Cryptography is the firmware's own.** The simulator links `firmware/crypto` for signature
  verification and never reimplements it in JavaScript (CLAUDE.md §22). The protocol signing keys are
  the simulator's existing test keys.
- **Constants.** A default model value with no derivation (a default NTC reading, a default impedance)
  is an unjustified choice and gets a row in `docs/status/unjustified-choices.md` in the change that
  adds it (CLAUDE.md §19).
- **Tests.** Each test of the above carries `@verifies REQ-SIMFW-nn` (CLAUDE.md §21).
- **`NP-SIM-001` and `simulator/HOWTO.md`** are updated in the change that builds each phase, and the
  standalone mode is documented as such (`D-2`).

## 11. Reuse as a bench test apparatus

**What is on file.** No document specifies a bench test apparatus. `NP-FW-BENCH-001` designs the
head-presence gate and what bench activity needs from it. Its §8.3 states the one requirement on a rig
that matters here: a rig legitimately has modules out, and the answer is a protocol that requires only
the modules present, never a presence bypass; `SEAT#` and `np_module_map_check_placement()` are not
relaxed (`NP-FW-BENCH-001` D-7). First-article tests (`NP-FAI-001` and the per-artifact lists) are
bench tests run by hand today. The reuse below is therefore a layering that keeps the option open, not
a rig design.

**Three layers, so that one of them is the only thing that changes between simulator and rig.**

| Layer | Holds | Simulator | Bench rig |
|---|---|---|---|
| **Scenario** | A scripted sequence of `MODULE_*` messages with expected observations: "fail `socket_pwm_set` on socket 12 once; expect the other sockets stay driven and the cranial enable stays asserted" | Written once | **The same file** |
| **Bridge protocol** | `MODULE_LIST`, `MODULE_STATE`, `MODULE_SET`, `MODULE_FAIL`, `FW_LOG` (§3.5) | The browser and headless tests speak it | The rig's operator tool speaks it |
| **Platform provider** | What answers the 119 seam functions | `firmware/platform_sim/`: every module simulated | A *rig* provider: real drivers for the hardware present, the simulator's module models for the hardware absent |

**What carries over.**
- **Scenarios and the bridge** are the same code. A scenario proven in the simulator is then run on the
  rig, which is how the simulator tells a developer what to ask of the hardware.
- **Module models** stand in for what a rig lacks. A rig with three tiles and no goggles uses the
  goggle's `SimModule` to answer the hub; the hub cannot tell which seams are real.
- **The firmware process** (tasks, scheduler, log) is the same executable shape, with the provider
  swapped.

**What does not carry over.**
- **The sim platform layer never goes on a device** (`REQ-SIMFW-01`). A rig provider is a different
  layer: real drivers behind the same symbols. On a rig whose hub is the real i.MX RT1062, the firmware
  is the cross-compiled image and only the scenario and bridge layers are shared.
- **The three.js view** is a simulator feature.
- **Fault injection into live hardware is a different hazard.** In the simulator an injected fault
  hurts nothing. On a rig, a scenario that suppresses a real module's answer can leave a real emitter
  driven. `REQ-SIMFW-09` governs.

**Added requirements.**

| ID | Requirement | What fails if not met | Traceable to |
|---|---|---|---|
| **`REQ-SIMFW-09`** | A scenario run against real hardware may not inject a response that makes the hub believe a driven emitter is stopped, or a hot module cool. It may inject only the modules the rig does not have. The rig provider refuses an injection aimed at a module backed by real hardware. | A bench scenario defeats the interlock the bench exists to exercise, or leaves an emitter driven while the hub reports it stopped. | CLAUDE.md §4.2; `NP-FW-BENCH-001` D-7 and §8.2 |
| **`REQ-SIMFW-10`** | Where a scenario run on a rig produces verification evidence, the scenario runner, the bridge and the module models it relies on are validated for that use under the quality system, and the evidence names their versions. Simulator runs remain excluded by `REQ-SIMFW-06`. | A defect in shared test code is silently a defect in a verification record. | ISO 13485:2016 §4.1.6 (software used in the quality system), to be confirmed by Quality; `REQ-SIMFW-06` |

**Questions for whoever owns bench and first-article test (`OI-SIMFW-10`).** Does a rig exist or is one
planned? Is the hub on it the real i.MX RT1062, a development board, or a host process? Which
first-article items would be scripted? Is evidence from a scripted run acceptable in place of manual
steps (`REQ-SIMFW-10`)?

## 25. The digital-twin rule (the principal, 2026-11-09; `OI-SIMFW-36`)

**Rule.** The simulator works as much like the real apps and hardware as it can. (1) The app that drives the simulated hardware contains all the functionality of the app that drives the real hardware. (2) All the hardware has a digital twin: a simulated version that runs all the same software the real hardware runs, simulates the effects the real hardware has, and returns simulated versions of the information the real hardware returns. A control on our hardware is an input to its twin and enters the software where the real one does. `OI-SIMFW-28` is the same rule applied to what the page could command.

**What this is not.** Nothing here makes a twin verification evidence (`REQ-SIMFW-06`); the rule raises how much the simulator is like the device and does not change what it can show. It adds no hardware figure and sets no limit.

**Where the simulator stands against it, read from the tree on 2026-11-09.**

| Rule | Today | Gap item |
|---|---|---|
| The app is the real app | The page runs a JavaScript session model; the NPPS parser is the one shared piece (§1). The page's controls send the bridge's own commands (§23). | `OI-SIMFW-37` |
| The app and twin speak the device's protocol | The bridge turns JSON into harness commands that call the drivers directly. The hub's `np_protocol.c` is linked, the apps' wire path is not on the page's route. | `OI-SIMFW-38` |
| Each part runs its own software | The hub's drivers (§12 to §20, §24) and the safety MCU's sources (§22) run. Other parts are not shown to run here. | `OI-SIMFW-39` |
| Effects and returned information match the hardware's | Drivers get plausible answers, marked as such (`REQ-SIMFW-04`); the page draws what the hub commanded and the MCU enabled (§23). | `OI-SIMFW-40` |

**Order.** `OI-SIMFW-37` decides what the page hosts, and `OI-SIMFW-38` follows from it; `OI-SIMFW-39`'s inventory can start now and is independent; `OI-SIMFW-40` goes modality by modality. Each is its own change with its own open item, and none of them is a detail of another.

## 26. The app's protocol upload over the hub's own transport, as built (`OI-SIMFW-38`, `REQ-SIMFW-17`)

The first slice of the twin speaking the device's protocol (§25). What the real app does: it compiles a protocol (a header, up to 64 commands and a zeroed 64-byte signature slot: `hubCompiler.ts`), a signing service fills the slot, and the app writes the framed bytes to the hub over BLE GATT or USB-C CDC. The hub's transport reassembles them (`np_transport.c`); `task_protocol_rx` takes the blob out, hashes it (`np_upload_check.c`, `SWR-UP-01`), loads it (`np_runner_load`) and notifies the app of the verdict in a 34-byte frame.

**What the first run showed (`OI-SIMFW-42`).** The golden protocol, signed with the TEST key and framed, is refused as a bad signature. ## 31. The hub's own tasks running a session, as built (`OI-SIMFW-45`, `OI-SIMFW-50`, `REQ-SIMFW-23`)

**What this is.** The twin now runs the hub's own boot path and its five tasks, so a protocol the hub accepts (§26) starts a session. `hub_boot` runs `np_hub_control_app_main()` from `np_hub_control_main.c` unchanged: the device's boot ordering (the factory-reset boot check, the log backend, the session log and count, the registry scan, the logger lock, the runner), then the five tasks. `task_protocol_rx` takes the blob the app wrote, `np_runner_load` admits it, `task_hub_control` runs `np_runner_run`, and the hub's own module drivers command the sim modules through the seams, with the real safety MCU model (§22) answering for the enable lines. The hub's own `task_safety_heartbeat` beats the MCU. Nothing here is verification evidence (`REQ-SIMFW-06`).

### How time works, and why (the decision `OI-SIMFW-45` asked for)

What a task, a tick and a timeout mean on the host was the central question, and `UC-124` already made the safety MCU run against a virtual clock. **Three ways were open** (they are the options of Q1 in `docs/human-input/oi-simfw-04-clock-domains.md`, which has not been sent):

| Way | Why it was not taken, or why it was |
|---|---|
| The FreeRTOS POSIX port, driven by the harness's clock | **Not taken.** The port ticks from a host timer, so a run is not repeatable and cannot be tied to the safety MCU's clock (`REQ-SIMFW-22`a). Replacing its tick source means a shim around vendored SOUP, and whether the port then schedules the same way was **not tried**. |
| Running each task body as a step the harness calls | **Not taken.** `np_runner_run` and the heartbeat task are loops that block in the kernel (a delay, an event wait, a semaphore); calling them as steps would rewrite them. |
| **A virtual-time cooperative scheduler in the sim layer (taken)** | `firmware/platform_sim/src/np_sim_kernel.c` defines the kernel calls the hub makes (task creation, delays, event groups, binary semaphores, mutexes). Each task is the device's own function on a host thread, and exactly one thread runs at a time. A thread gives up the baton only in a kernel call; priorities are honoured (a task woken by a higher-priority one is preempted at that call), and equals take turns only at a block. Virtual time moves only inside `np_sim_kernel_run_ms()`, and only when every task is blocked: it jumps to the earliest wake (a delay's end, an event wait's timeout), a millisecond at a time while the safety MCU is attached, so its loop sees every millisecond. A 200 ms heartbeat is 200 virtual ms. |

**What the choice does and does not show.** It is repeatable (a test runs the same session twice and compares every reported state and its virtual time), it shares one timeline with the safety MCU model, and the five tasks' interactions (a protocol load waking the runner, the heartbeat, the idle detect pass under the session lease) are the device's own code. **It is a model of the kernel, not the kernel:** a task is never preempted between kernel calls (the device preempts on a tick), priority inheritance on the lease and logger mutexes is not modelled, and no stack is measured. A scheduling defect that needs a tick to land inside a statement cannot appear here. `OI-SIMFW-75` asks the principal whether that is enough. **The clock domains of `REQ-SIMFW-22`(b) to (d) are not built:** the hub's tasks and the safety MCU read the one virtual counter, which is the decided model's default case (every offset at zero). The epoch of the counter is the host's uptime at the first virtual advance, so an absolute `t` differs between runs and every difference is the same.

**What the first runs showed.** None of it is decided here.

- **The hub's own code never sends the session signature (`OI-SIMFW-74`).** `REQ-FWHUB-18` has the hub send `np_safety_spi_send_session_sig` after the first RUNNING heartbeat, and nothing under `firmware/` outside the tests calls it. - **An electrical line was withheld after the signature in the tDCS run.** The hub's tDCS driver commanded the pair (a ramp) and requested the line; after the signature the MCU still withheld it, and its withhold report named the declaration and geometry gates (status OK, no fault). The runner sends the channel declarations at `np_runner_run`'s start, and §23 records that the MCU's session-start reset wipes a declaration sent before the session starts; **the order was not traced here**, so whether the runner's declarations are what the reset wiped is unverified (`OI-SIMFW-74`).
- **A stop ends as `fault`.** Read it as the device's own behaviour (above), not as a twin defect; the page shows `fault` and the fault LED after a person's stop.
- **The twin cannot sign a protocol whose signed hex exceeds about 230 bytes (`OI-SIMFW-77`).** `proto_sign` reports the signed blob in one event, the event buffer is 512 bytes, and the line is cut: the `interval` golden (280 bytes) cannot be signed through the twin. The goldens used here are 150 to 170 bytes.
- **A PBM session refuses its drive.** The shipped governor refuses every load (`OI-SIMFW-11`), so a PBM protocol runs and the hub's dispatch refuses its commands; no PBM scenario is in the suite.

**Gaps (`REQ-SIMFW-13` asks that they be listed).** The kernel is a model and a task is not preempted between its calls (`OI-SIMFW-75`). No line is granted by the device's own code alone (`OI-SIMFW-74`). The page cannot start a session (it has no hub compiler: the compile is the app's, `OI-SIMFW-44`), the Compose host does not boot or tick the twin, and its helmet view takes no per-module state from a running hub (`OI-SIMFW-76`); the whole page was not run here (the sandbox cannot reach the CDN the page loads its 3D library from), only the panel's code, in headless Chromium. The twin's storage is files, and a session's records are in them (§33); the device's `np_reset_marker.c` is not linked, because it defines the same two seams as the factory-reset module's host model that runs instead (so the boot's Config check is that model's, not the Config partition's). A failed `configASSERT` aborts the process (the device's hook halts). Line coverage of the newly linked sources was not re-measured. Not run: the radio and USB transports (`OI-SIMFW-46`), the Swift, C# and Android hosts, `./gradlew` (the app was not touched). Nothing here is verification evidence (`REQ-SIMFW-06`).

## 32. The HRV biofeedback library, reached (`OI-SIMFW-60`, `REQ-SIMFW-24`)

**What this is.** `np_mod_vns.c` starts the HRV session (`firmware/hrv_biofeedback/`) when a VNS command names a protocol, and the library was linked and barely run (§28). Its DSP is reached here by playing the three feeders it was written for, which **nothing in the device's own code supplies** (`OI-SIMFW-78`): `np_hrv_session_push_ppg` (200 Hz), `np_hrv_session_push_eeg` (500 Hz) and `np_hrv_session_tick` (10 Hz). `np_sim_hrv_harness.c` plays them with **synthetic** signals against the session the driver created (the library's own `np_hrv_session_create` returns the existing context while one is allocated, so no firmware change was needed to get it). What the session reports comes out as its own coherence result and the record it hands the logger at its end (`np_log_hrv_session`, whose `fw_log` event now carries the record's fields). Nothing here is verification evidence (`REQ-SIMFW-06`), the signals are no person's data (`REQ-SIMFW-08`), and a pass says nothing about a real heart.

| Piece | Where | What it is |
|---|---|---|
| The feeders | `firmware/platform_sim/src/np_sim_hrv_harness.c` | `hrv_run <ms> <bpm> <rsa_ms> <drift_ms> [<alpha_uv> <theta_uv>]` advances virtual time a millisecond at a time and plays the three feeders: a Gaussian pulse train for the PPG (period from `<bpm>`, plus a 0.1 Hz sinusoid of `<rsa_ms>`, plus `<drift_ms>` a beat), an 8-channel EEG of 10 Hz and 6 Hz sinusoids, and a tick every 100 ms. `hrv_state` reports the library's coherence result; `hrv_reset` forgets the beat phase. With the hub booted (§31) the same time moves through the kernel model. |
| The two direct calls | same | `hrv_pacer <ms> <peak_bpm> [<rate> <personalised>]` and `hrv_eeg_bands <alpha_uv> <theta_uv> <hrv_valid> <score>` call the library's own public functions, because the session keeps their results to itself (its display callback is NULL in the driver and its context is opaque). |
| The record | `np_sim_log_wrap.c` | The `np_log_hrv_session` event carries duration, protocol, target rate, R-R count, taVNS onsets and the coherence figures. |
| Tests | `firmware/platform_sim/tests/np_sim_hrv_tests.c` | Eleven scenarios, the thirteenth suite, each in a forked child with an alarm. |

**Where the paths came from.** The row's closing condition is that the owner of `NP-FW-HRV-001` lists the paths a scenario must reach. No list was given, so the paths below are the library's public functions and the branches of `np_hrv_session.c`, `np_hrv_pacer.c`, `np_hrv_tavns_sync.c` and `np_hrv_eeg_biofeedback.c`; the owner may add to them.

**Lines reached (`sim-coverage.sh`, 2026-11-13, all suites).** Before, then after: `np_hrv_eeg_biofeedback.c` 0 % to 100 %, `np_hrv_ppg.c` 13.2 % to 97.1 %, `np_hrv_coherence.c` 12.4 % to 97.7 %, `np_hrv_tavns_sync.c` 21.1 % to 86.8 %, `np_hrv_pacer.c` 22.7 % to 97.9 %, `np_hrv_session.c` 40.6 % to 95.3 %; `np_mod_vns.c` is unchanged at 96.0 %. A line reached is not a requirement verified.

**What the scenarios cover.** The session's own timer is never reached without a feeder (1300 virtual seconds, no coherence, no record). Coherence needs 64 R-R intervals (30 s of beats gives NOT_READY; 90 s of a 0.1 Hz rhythm gives a valid score of 10 and an RMSSD near 35 ms). The peak detector refuses an interval above 2000 ms, reads every second beat of a 240 ms train as a 480 ms interval, and its buffer saturates at 256. The taVNS gate opens once on a 5 s run of shortening intervals, opens again after the 6 s failsafe on a 15 s run, and never opens under the EEG-dual protocol. A fed session ends itself at 1200 s with one record, and a later driver stop writes nothing; a new session then starts. The pacer sweeps from 4 breaths a minute, refuses to finalise a sweep still running, and settles on the rate where the synthetic coherence peaked (5.5, 6.5); a personalised rate is taken as it is. The EEG bands follow the signal (alpha above theta for 10 Hz, theta above alpha for 6 Hz), and the adaptive step gives no nudge without a valid HRV, down by 0.25 for a low alpha/theta ratio, up by 0.25 for a coherence under 5. The EEG-dual protocol ran 100 s of PPG and EEG through the driver's session.

**What the first runs showed.** None of it is decided here; each is for the owner of `NP-FW-HRV-001`.

- **Nothing feeds or ticks the session in the device's code (`OI-SIMFW-78`).** No caller of `np_hrv_session_push_ppg`, `_push_eeg` or `_tick` exists outside the library and its tests; the driver says the HRV module "owns its own FreeRTOS task" and the library has none. With the device's own code the session never produces a coherence and never ends by its timer (1300 s measured). The twin's feeders are its own, standing in for them.
- **The taVNS gate never reaches a stimulator or hears the safety MCU.** The session's `tavns_enable` and `tavns_disable` are empty ("stub, implemented by the platform HAL layer"), and `np_hrv_tavns_safety_mcu_response` has no caller. The sync's onsets are visible only as the record's count. The safety MCU still owns the enable line (`CLAUDE.md` §4.2); this concerns the library's advisory gate.
- **A finished RF sweep is never finalised by a session.** `np_hrv_session_stop` calls `np_hrv_pacer_sweep_finalise` only while the sweep is active, and finalise refuses while it is active (NOT_READY), so the call can never succeed; once the sweep is over the call is not made. A 900 s session that covered all seven steps recorded no personalised rate, while the library called directly finalised the same kind of sweep to the right rate. Read from the code, and shown by the two runs.
- **A starting rate in range is ignored.** The pacer sweeps from 4 whenever no personalised rate is given, whatever rate was asked.
- **A perfectly steady rhythm scores the maximum coherence.** With no variability the LF and HF powers are 0 and the ratio of two near-zero numbers gives 10. A flat rhythm is not a physiological one; the scenario pins the behaviour as found, and says to change the check when the owner decides what it should score. (A first version of the generator made this result depend on the host's uptime, through the beat's phase on the sample grid; the phase is now fixed and the result repeats.)
- **The detector reads a rate above 200 per minute as half of it** (240 ms beats came out as about 38 intervals of 480 ms in 20 s), a consequence of the 300 ms refractory period that the code's own comment calls the upper limit.
- **The STANDALONE protocol cannot be started through the driver:** `hrv_proto` 0 means no session, and the library's protocol 0 is STANDALONE.
- **The telemetry readouts are not the library's.** `np_mod_vns_hal_get_rmssd`, `_coherence` and `_hr_bpm` are platform seams, which the twin answers from the values a scenario gives the clip; the device's implementation of them is not in the tree (`firmware/platform/` traps), so what connects the library's coherence to the driver's telemetry is not shown here.

**Not reached, and why.** `np_hrv_session_create` with no end callback and `np_hrv_session_start` on a null or running session, and the taVNS configuration refusal in the session and in `np_hrv_tavns_init` (the driver gives the session no taVNS settings and never starts one twice); the display callback (the driver passes NULL); `np_hrv_tavns_safety_mcu_response` (no caller); `np_hrv_rr_get` with an index out of range, `np_hrv_ppg_rmssd` with too few intervals, and three error returns of `np_hrv_coherence.c` (nothing in the session can produce them). The first four are reachable only by a direct call of the library, which `np_hrv_session_tests.c` already makes for the taVNS configuration.

**Gaps (`REQ-SIMFW-13` asks that they be listed).** The feeders are the twin's and synthetic, and no bridge command or page control plays them (the C suite and the spike's text commands only). The coherence a real PPG would give is not shown: the pulse is a Gaussian, with none of a real waveform's noise, motion or dicrotic notch. The dual biofeedback's output (the pacer rate it adapts) is visible only through the direct call (`OI-SIMFW-78`). Nothing here is verification evidence (`REQ-SIMFW-06`).

## 33. The hub's partitions, stored in files (`OI-SIMFW-51`, `REQ-SIMFW-25`)

**What this is.** Every partition the hub's own code writes to is now a littlefs instance, in the device's own geometry, over a **file** on the host that nobody can name (`REQ-SIMFW-21` (a), (b), (d)). The Config instance used to sit on a RAM medium; the UHDR and SHDR partitions were not modelled at all, and the session logger wrote to a host model that kept bytes in memory. Now a session's records go through the device's own logger and log backend into the UHDR and SHDR partition files, the session count and the module map are kept in the Config file, and all three come back from the file after littlefs is unmounted and mounted again. What is in the files is **synthetic** (`REQ-SIMFW-08`): whatever the hub's code writes to a twin that no person wears. UHDR is plaintext here; the device encrypts it at rest under a key NeurOne never holds, and the twin holds no key (`OI-SIMFW-52`). Nothing here is verification evidence (`REQ-SIMFW-06`).

| Piece | Where | What it is |
|---|---|---|
| The medium | `firmware/platform_sim/src/np_sim_storage.c`, `include/np_sim_storage.h` | One backing file per partition: made in the system temporary directory (`TMPDIR`, else `/tmp`) under a random name by `mkstemp`, mode 0600, and **unlinked at once**, so it has no name and cannot outlive the process whatever ends it. It is sparse: Config is 16 MiB, SHDR 512 MiB and UHDR 7,238,320,128 bytes (6,903 MiB), and in the run measured here the host allocated 16 KiB, 8 KiB and 16 KiB of them. An erase moves nothing (a block never written reads as zeros) and a sync flushes nothing to the host's disk, so no durability is claimed. If no file can be made the boot is refused and the twin does not fall back to memory. |
| Config | `np_sim_gatt.c`, `np_sim_storage_up()` | The device's own Config-instance geometry over that file; the RAM block device the hub's power-loss tests use (`np_lfs_powerbd.c`) is no longer in the twin. |
| UHDR and SHDR | `np_sim_storage.c`; `np_lfs_log_instance.c` | The device's own geometry and validation for each log instance, formatted new, mounted, the allocator primed once as the glue must. UHDR holds `/uhdr/sessions/<session counter, 20 digits>`, an exclusive create of one file per session, as `np_log_backend.h` states; SHDR holds one append-mode file. |
| The log file layer | `np_sim_storage.c` | `np_log_hal_part_open`, `_append`, `_sync` and `_close`: **the twin's own**. The device's board layer does not implement them (`firmware/platform/` traps), so the twin gives each the behaviour `np_log_backend.h` states for it. | The other sources | `CMakeLists.txt` | `np_lfs_log_instance.c`, `np_hexmap_nvram.c` (the module-map blob on Config, replacing the two stubs `np_sim_spike_link.c` carried), `np_map3_record.c` and `np_hexmap_inventory.c`. `np_adaptation_log.c` and `np_pbm_cal_bridge.c`, which the row named, were linked with the hub's boot path (§31). |

**What the scenarios show.** Each partition is a mounted instance backed by a file of exactly the instance's size, with no name, mode 0600 and under 64 MiB allocated. A completed 3 s session left one UHDR session file with bytes in it and bytes in the SHDR log (34 bytes in the first run); after both log instances were unmounted and mounted again the same files with the same sizes came back, and the UHDR file's first bytes read back. A second session made a second UHDR file, left the first the size it was (a closed session file is never written again) and grew the SHDR log. The device's session count in Config was 1 after one session and 1 after the Config instance was unmounted and mounted again, and the module map persisted through `np_hexmap_nvram.c` (a 14,012-byte blob) and read back as one `np_module_map_blob_verify` accepts. With the temporary directory pointing at a directory that does not exist, `hub_boot` did not boot. Map 3's rows round-trip through the device's own encoder and scanner, a damaged second row ends the valid prefix at the first, and a journal cut short is a torn tail. A socket poll by `np_hexmap_poll_socket` returns an error and the twin reports the unrouted `np_pbm_hal_i2c_read`: the smart-module register tunnel has no route (`OI-SIMFW-53`, `OI-SIMFW-57`).

**What `REQ-SIMFW-21` still asks and this does not do.** (a) is met for the three partitions, not for all state: the cervical fault summary's blob (`np_cvfs_hal_*`, `np_sim_spike_link.c`), the safety MCU's OTP and flash model, the TEST keys and the modules' state are still memory. (b) is met where the host lets a file be unlinked while open (POSIX); the deletion on exit and the removal of a dead session's leftovers at every start, which a host without it needs, are not built. (c) and (e) to (o), the save, its retention and the container mapping, are `OI-SIMFW-05`'s and not built.

**What the first runs showed.** None of it is decided here.

- **The device's board layer has no log file layer** (`OI-SIMFW-79`). The twin's `np_log_hal_part_*` is its own, written to the header's text. Whether the device's will agree on the SHDR file's name, on the session file's name or on when UHDR is mounted is not shown. The device mounts UHDR only after the user's key unlocks it (`np_uhdr_key_unlock`); the twin has no key and mounts it at the first session file.

- **The twin lost nothing it used:** the power-loss injection of `np_lfs_powerbd.c` was available to a test and no twin scenario used it. It is not modelled now (below).

**Gaps (`REQ-SIMFW-13` asks that they be listed).** The eMMC's timing, wear and power loss are not modelled, and nothing is flushed to the host's disk. UHDR is not encrypted and no key exists. The files are never kept (no save), and a host that cannot unlink an open file is not handled. The log file layer is the twin's, not the device's. The module map is persisted by the hub's code only when a scenario calls it; the hub's own call sites were not traced. No page control reads the partitions. Not run: `./gradlew`, the wasm bundle, a non-POSIX host. Nothing here is verification evidence (`REQ-SIMFW-06`).

## 34. The UHDR key scheme, run (`OI-SIMFW-52`, `REQ-SIMFW-26`)

**What this is.** `np_uhdr_key.c` is the device's own two-layer key lifecycle (`NP-FW-EMMC-002` §C): provision mints a key and wraps it under a credential, unlock reads the record and opens it, background zeroes the key, change-credential wraps the same key again. It is linked unmodified and runs on four commands, `uhdr_key provision|unlock|background|change` and `uhdr_key status`, each reported as one `uhdr_key` event. Nothing is verification evidence (`REQ-SIMFW-06`).

**What its seams are.** The device's source offers its eight platform seams only under `NPTEST_HOST`, so they are **that file's own host model**: the Argon2id and the AES-GCM are SHA-256 constructions its comment calls "NOT cryptography", the TRNG is a counter, the device-fused key is a constant in RAM (a "different device" is a different constant), the Config record is a RAM variable and the mount records only that it was called. What runs is the lifecycle's logic and its refusals: a wrong credential fails the tag check, a tampered record fails it, a change re-wraps the same key and background locks. The cryptography is not run, and every event says so (`"model":"host-model-not-cryptography"`). `OI-SIMFW-80` asks the principal whether the twin should link the Rust primitives of `CLAUDE.md` §22 instead.

**What it holds.** Synthetic only (`CLAUDE.md` §5.1, `REQ-SIMFW-08`). A credential is a number 0 to 15 naming the fixed text `np-sim-synthetic-credential-NN`; the bridge sends a whitelisted operation and that number and nothing else, so a client cannot supply a credential, let alone a person's (`UC-184`). No key byte is reported, wrapped or plain; an event carries the status, the lock state, the mount count and whether the stored record's wrapped field differs from the key (it must).

**What it does not do.** UHDR in the files of §33 is still plaintext: the session logger does not take the key this scheme mints, because the device mounts UHDR with it through a seam whose host model records the call and nothing more (`OI-SIMFW-80`). The record is not in the Config file. The `anon/`, `edf/` and `shdr/np_accel_shdr.c` services are not linked. The factory-reset module's wipe steps are linked and no scenario reaches them. Eight seams moved from `absent` to `firmware-host` in `np_sim_seam_routes.txt`.

**Scenarios** (`np_sim_hub_run_tests.c`, five): the lifecycle, a wrong credential, a changed credential, no key in any event, a bad command. The bridge test checks the whitelist.
