## 1. What is known

- **The decision, verbatim:** "Since this will also be used as part of the test bench, store everything to a file (including UHDR and SHDR records - and synthetic state). The file should be temporary unless there is a specific request to save it for later examination. Otherwise, the temporary file should disappear when the user exits the session."
- **What is built today:** one RAM medium under the Config instance; no file, no path (`NP-SIM-FW-001` §27).
- **The existing block device can sit on a file unchanged** (probe run 2026-11-11, scratch code, not committed): `np_lfs_powerbd` takes a caller-owned buffer, and a shared mapping of a file works as that buffer. On the Config geometry (16 MiB) littlefs formatted, mounted and wrote through it; the file reopened by path in a new mapping mounted and read the data back; and after the file was unlinked while still open the mapping kept working and the path was gone. **Not tried:** the SHDR (512 MiB) and UHDR (6,903 MiB) geometries, any host but Linux, and a crash of the host.
- **`REQ-SIMFW-08` stands:** the twin's storage is synthetic, it never mounts, opens or accepts an image of a real UHDR or SHDR partition, and it holds test signing keys only. `CLAUDE.md` §5.1: NeurOne never has access to UHDR.
- **`REQ-SIMFW-06` and `REQ-SIMFW-10`:** a simulator run is never verification evidence; a scenario run on a rig could be, with the runner and models validated.
- **The twin is to ship as one local container** (`NP-SIM-FW-001` §9, D-2, decided; not built). Inside a container the "user's machine" is the container's filesystem unless a directory is mounted from the host.

## 3. Questions

**Q1. Where does the temporary file live, what is it called, and who may read it?**

- **(A) The system temporary directory, a random name, owner-only (0600 on POSIX).** Costs: on a shared machine the name is visible to other users even though the content is not; in the container it is the container's own temporary directory, gone with the container. Gains: nothing to configure; the operating system's own cleanup applies.
- **(B) A directory the twin owns under the user's home or data directory, random name, owner-only, the directory owner-only too.** Costs: a new directory to create and to document; nothing else cleans it. Gains: not visible to other users at all; leftovers are easy to find (Q2).
- **(C) A directory named by the person who starts the twin, no default.** Costs: the twin does not start without it; a path now comes from outside, and it must be shown that it can only ever name a new file (Q4). Gains: a bench can put it on the disk it wants.

One file holding every partition, or one file per partition, is an engineering detail unless the principal wants it fixed; say if so.

**Q2. How is "disappears when the user exits the session" made true?**

- **(A) Delete on normal exit only.** Costs: a crash, a kill or a power cut leaves the file behind, so the sentence is not true in those cases. Gains: simplest; the file has a name all session, so saving (Q3) is a copy by name.
- **(B) Create, then unlink while open (POSIX).** The file has no name from the first moment and cannot outlive the process, whatever ends it. Costs: there is no name to copy from, so saving (Q3) must copy through the open handle or be chosen at start; Windows has no identical operation (the nearest are a delete-on-close handle, which the system honours when the last handle closes, including after a kill, but which other programs can open differently; the twin does not run on Windows today). Gains: true after a crash or a kill. Shown to work with the existing block device on Linux (section 1).
- **(C) Delete on normal exit, and at every start remove files left by sessions that are no longer running.** Costs: a leftover survives until the next start, which may be never; the twin has to tell a dead session's file from a live one's (a lock or a process id, and process ids are reused). Gains: works the same on every host; keeps the name for Q3.
- **(D) B where the host allows it, C elsewhere.** Costs: two behaviours to test and to explain. Gains: the strongest guarantee each host can give.

Also for the principal: **is a leftover after a host power cut acceptable** if it is removed at the next start, or must it be impossible? Only B (and its Windows nearest) makes it impossible, and only while the file is unnamed.

**Q3. What is "a specific request to save it for later examination"?**

Who asks: (i) the person at the page, (ii) the person who starts the twin, (iii) a bench script. Any or all.

- **(A) A choice at start only** (a flag or a setting when the twin is launched). Costs: the wish to keep a run usually comes after something went wrong, when it is too late. Gains: no command during the session; the file can be named from the start; nothing a browser client sends can cause a write to disk.
- **(B) A command during the session** (a button on the page and the same message from a script). Costs: a client message now causes a file to be written, so the bridge must validate it as it does every other command (`REQ-SIMFW-12`): the client may ask for a save but may not supply the path. Gains: a run can be kept after the fact.
- **(C) Both.**

Where the saved copy goes and what it is called: **(1)** a fixed directory the twin owns, with a name the twin builds (date, time and a random part), nothing from the client; **(2)** a directory named at start by the person who launches the twin, name built by the twin; **(3)** a path the requester gives in full. Option 3 lets a client choose where on the machine a file is written, which the bridge's rules exist to prevent. In the container, a saved copy survives only if the directory is mounted from the host; say whether that mount is part of the product.

Also: **how long is a saved copy kept, and who deletes it?** The sentence does not say. Options: until the person deletes it; or the twin lists and offers to delete saved copies.

**Q4. What keeps a real person's UHDR out of the twin, and is the synthetic UHDR in the file encrypted?**

What keeps real UHDR out:

- **(A) The twin only ever creates its file and never opens an existing one.** No command, flag or message loads a file. A saved copy (Q3) is for examination by other tools and cannot be loaded back. Costs: a saved run cannot be resumed or replayed from its state. Gains: `REQ-SIMFW-08` holds by construction: there is no input through which any image, real or not, enters.
- **(B) The twin may load a file, but only one it wrote, proved by a mark it checks** (for example a keyed tag under a key that exists only in the twin). Costs: the mark and its check are new security-relevant code (Rust, `CLAUDE.md` §22); a check is weaker than having no door; a real partition image fails the check only if the check is right. Gains: a saved run can be resumed.
- **(C) As B, and also refuse anything that decrypts or mounts as a real partition would.** Costs: the twin would need to recognise a real image, which is hard to show complete. Gains: a second barrier.

Whichever is chosen, the twin holds TEST keys only and no production key (`REQ-SIMFW-08`), so a real UHDR partition, which is sealed under a key derived from the user's biometric (`CLAUDE.md` §5.1), could not be read by it even if it were loaded. That is a second line, not the first.

Is the synthetic UHDR in the file encrypted:

- **(1) Encrypted as the device does it, under a TEST key.** The twin runs the device's own UHDR key and storage code (`OI-SIMFW-52`, not built), so what is in the file is what the device would write. Costs: waits for that code to run in the twin; a saved file needs the TEST key to examine. Gains: the twin exercises the real path, which is the reason for a twin; the bench sees what the device stores.
- **(2) In the clear, for the bench.** Costs: the twin's UHDR partition is then not what the device's code writes, so the device's encryption path is not run and a bench result about storage says nothing about the device; a habit of clear UHDR files, even synthetic, is one to weigh against `CLAUDE.md` §5.1's "protection only goes up" (that rule is about real UHDR; whether it should also bind the synthetic case is the principal's to say). Gains: a saved file can be read with ordinary tools.
- **(3) Encrypted in the file, with a separate export in the clear on request.** Costs: two forms to keep in step. Gains: both uses.

**Q5. What may a saved file be used as evidence for?**

- **(A) Nothing. It is a debugging aid.** Consistent with `REQ-SIMFW-06` as written. Costs: a bench run's saved file cannot go into a design-history file. Gains: no validation burden on the twin, the bridge or the file format.
- **(B) Nothing from a simulator run; from a bench run on a rig, a saved file may be verification evidence under `REQ-SIMFW-10`.** Costs: the file store, its format and the save path fall under the validation `REQ-SIMFW-10` requires, and the file must record what produced it (rig or simulator, versions) in a way that cannot be mistaken; `OI-SIMFW-10` (whether a rig exists, and what its hub is) is still unanswered. Gains: the bench use the principal named produces something that can be kept as a record.
- **(C) Decide when a rig exists.** Costs: the file format is designed without knowing whether it must carry provenance. Gains: nothing is promised early.

Whichever is chosen: should every saved file carry, in itself, a statement of what it is (simulator or rig, synthetic data, not verification evidence unless B applies)? Recommended yes, so a file found later cannot be taken for something else.

Costs: it is a named file for the whole session, so a crash, a kill or a power cut leaves it behind, which is the leftover Q2 option D was chosen to avoid; it is then a saved file that was never closed, under the open rules of M1 and M3; and every write of the twin's storage lands in the person's directory, a mapped one in a container. Gains: one file, one write path, and the file is current to the last write. How it fits the same sentence: the session's working writes are the updates.
- **S2. What the command during the session carries.** The bridge validates every command and puts no client string into a command line of the firmware process (`REQ-SIMFW-12`). The command may ask for a save, and may carry a name, since the principal's direction is that the person may pick one. The directory is the open point of Q3: unless the principal decides otherwise, it would come from a place the twin controls (the remembered directory or the one set at launch) and not from the client's message. What the bridge would then refuse, for confirmation: a save command that carries a directory or any path separator; a name that is not a plain file name (one with a separator, a parent-directory component, a control character, or a length over a limit to be set); a name that does not end in the twin's extension once that exists (question C of `oi-simfw-05-saved-file.md`); and anything it cannot validate, which is refused and said so, never altered and accepted. An unattended bench script can use either way, the launch flag or the same command sent by the script, and neither may wait on a prompt (R3).
- **S3. What a second save command does in the same session.** **ANSWERED 2026-11-11 (the principal), verbatim:** "A second save in a session (Not a 'save as') updates the currently open file." **Decided:** a second save command in a session that is not a 'save as' updates the file the session already has open. It agrees with the answer on overwriting (a session may keep updating its own open file) and with the 'save as' answer (a 'save as' closes the previous file, which then cannot be updated). Recorded as `REQ-SIMFW-21` part (l). Not built. **Not said:** how the file is updated (replace with the latest snapshot, a live mirror, or append), which is question M2 of `oi-simfw-05-saved-file.md` and stays open; whether a save requested at launch behaves the same (S1); and what a plain save does when no file is open. For the last, it is supposed that the first save of a session creates the file, to be confirmed by the principal and not decided here. *As first drafted:* It updates the session's file, which the principal's answer on overwriting allows ("a save can continue to update a file that was created by that same session"). Whether updating means replacing with the latest snapshot, a live mirror or appending is question M2 of `oi-simfw-05-saved-file.md`, open; and whether a second save can instead start a new file depends on what "closed" means (M1 there), open.
- **S4. The default when nothing is requested.** **CONFIRMED 2026-11-11 (the principal), verbatim:** "The default when nothing is requested is no saved copy" When no save is requested, at launch or by a command, there is no saved copy. This restates the principal's original sentence ("temporary unless there is a specific request to save it"), so it is a confirmation and not a new decision. It is already carried by `REQ-SIMFW-21` parts (b) and (c) ("a run nobody asked to save leaves nothing behind"); no part was added. When the working file disappears is as already recorded and no more is said here: it depends on the corrected meaning of "session" and on the open question about Q2 option D (N2). *As first drafted:* No saved copy is made, and the working file disappears when the user exits the session. That is the principal's original sentence (`oi-simfw-05-storage-block-device.md` §5) restated, not a new decision. To confirm that it still reads so now that a save can be asked for in two ways.
- **S5. How a launch-time request is given in a container.** A launch flag and the directory mapping are both set when the container starts, so both belong to whatever starts it: the command line a person types, or the host-side launcher of question D of `oi-simfw-05-saved-file.md`, which is not designed. A launch-time save with no mapping given is the case of C2.

**Consequences of the retention and who-deletes answers, each a question with options and costs; none is decided.**

- **R0. Points the retention answer left to settle** (the last of them, the clock, is kept as R5 below):
  - Is the week counted from when the copy was saved, or from when it was last opened?
  - What may the configured value be: is there a minimum, a maximum, and is a value meaning "do not expire" allowed?
  - Where is the setting kept? The same local preference store as the remembered directory would be the natural place (question F of `oi-simfw-05-saved-file.md`, open).
  - The clock. A retention period of a week is real time. The twin's time model is a virtual timeline with clock domains (`OI-SIMFW-04`, decided, not built), and a virtual clock can be advanced a week in a moment. So expiry has to be judged by the host's wall clock and never by the twin's virtual time. This is stated as a consequence to confirm, not as a decision.
- **R1. The twin must know where its saved copies are.** To list expired copies it needs a record of each copy it saved: the path, when it was saved, and either the period in force then or the current setting (which of those two governs is itself to be said). It cannot scan a whole disk, and it must not take a file for its own by name alone (R2).
  - **(a) A local index,** kept in the same preference store as the remembered directory (question F of `oi-simfw-05-saved-file.md`, open). Costs: an index of paths is a stored list of where the person keeps saved runs. It is not UHDR and not SHDR, but it reveals directory names, which under a home directory usually contain a login name, and the file names in it contain the pseudonymous id, so the index sets a login beside a pseudonym on that machine; it goes stale when the person moves, renames or deletes a file, so every entry has to be checked against the disk before it is listed; a directory may no longer exist or may be on removable or network media that is absent, and an absent file must not be reported as deleted or as expired. Gains: finds copies in every directory the person used.
  - **(b) Scan only the remembered directory.** Costs: misses every copy saved elsewhere, so if the person has used several directories the list is incomplete and says nothing about what it missed; a scan reads every file's header in that directory (R2). Gains: nothing is stored but the one path already stored.
  - **(c) Both:** the index, checked against a scan. Costs: those of both. Gains: a moved file inside the remembered directory is still found.
- **R2. What counts as the twin's own file.** The means would be the unique extension and a header with a magic number and a version (questions C and E of `oi-simfw-05-saved-file.md`, both open). Whatever they turn out to be, two rules follow from the decision and from `REQ-SIMFW-08` and are stated for confirmation: the twin never offers to delete a file it does not recognise as its own, and a file that only carries the extension, a renamed image of a real partition included, is not its own. To confirm, and to say whether the extension alone is ever enough (this draft assumes not).
- **R3. When the listing is shown.** (a) At every start of the twin. (b) Only when the person asks, from a menu. (c) Both. And for a run by a bench script with nobody present: a prompt that waits for a person would hang the script, so a script run either (i) skips the offer entirely and says so in its output, or (ii) lists and deletes only on an explicit command in the script. Costs: under (a) a person is asked about old files every time they start work; under (b) expired copies are never mentioned unless someone looks, so the period has little effect; under (ii) a script can delete, which is a person's choice made ahead of time and has to be accepted as such.
- **R4. What the offer looks like, and what happens if it is declined.** Delete all, delete one by one, or keep. Is a declined copy offered again at every start? Can the person extend a copy's period, or exempt it from expiry? What the list shows: this draft supposes name, size, saved date and expiry date, and notes that the name holds only the pseudonymous id and a timestamp. Costs: "offer again every time" nags; "never again" makes the period a one-time prompt; an exemption is one more stored setting per file (R1).
- **R5. The clock.** Expiry is judged by the host's wall clock and never by the twin's virtual time (`OI-SIMFW-04`: a virtual timeline can be advanced a week in a moment). Kept from the retention answer, still a consequence to confirm.
- **R6. How a delete is done.** (a) An ordinary delete. Costs: the bytes stay on the disk until reused. (b) Overwrite, then delete. Costs: slower; on solid-state disks, copy-on-write and network filesystems an overwrite does not reliably reach the old bytes, so it promises more than it delivers; more code. What it would add: the files are encrypted at rest (the principal's direction) and hold synthetic records, so an overwrite adds protection only against someone who has both the disk and the key; under a key that is not shared that is nobody new. Not chosen.

**Consequences of the container answer, each a question with options and costs; none is decided.** (The point as first drafted read: "What happens in the container. A directory the person picks is a directory on the host; the container sees it only if it is mounted. Whether the mount is fixed when the container starts, and what "pick" then means, is not said.")

**The principal, 2026-11-11, verbatim, on the container directory (C1 and C2):** "If a container must map a directory when the container is created, then we need to map the internal container directory a priori even if we don't know if a save request will come. 3. By contrast, when the twin runs locally, not in a container, the directory is choosable, as the principal's earlier direction already said.

**Questions the container-directory answer raises; none is decided.**

Candidates, none chosen: `/var/lib/neurone/saved` (follows the usual place for a program's own data); `/neurone/saved` (short, at the root, plainly the product's); `/saved` (shortest; the most likely to collide with something else). A name would be checked against every other path the container image uses and against the directories a base image already has; the container is not built (D-2), so there is nothing to check against yet, and the choice has to be re-checked when it is.
- **D2. Options (a) and (c) not taken.** Who chooses the host directory, and when: at container creation by a host-side launcher (question D of `oi-simfw-05-saved-file.md`, not designed), or by a person typing the mapping into the command that starts the container. **Questions these answers raise; none is decided.**

- **V1. What "fix it" can mean.** A running container cannot gain a mount, so a missing mapping cannot be fixed inside the running container: the fix is to start the container again with the mapping, through the launcher. So "force the user to fix it before continuing" comes to this: the twin stops, says what to do, and does not continue. Does "not continuing" mean **(a) the twin exits,** with a message and a non-zero exit code (costs: the page loses its connection at once, so the message has to be somewhere the person will see it, V5; gains: nothing is left running in a state that cannot be used, and a script sees the failure), or **(b) the twin stays up and does nothing else** but show the message until it is stopped (costs: a container left running to no purpose, and a person may think it is working; gains: the page can show the message)?
- **V2. Unattended runs.** A bench script or a CI run has nobody to fix anything, and a prompt that waits would hang the run. What does an unattended run do when the mapping is missing? Refusing to start and exiting with an error is what "force" would reasonably mean there. And may a person deliberately run with no mapping, for example a throwaway run that will never be saved? The principal's "always present" and "force" both point to no. That is a reading to confirm, not a decision.
- **V3. What counts as "mapped".** From inside a container, a bind mount of a host directory, a named volume managed by the container runtime, and a temporary in-memory mount can all look like a mount; only the first is a directory the person can see on the host. Options: accept any mount (costs: a save into a volume or an in-memory mount is not where the person expects, and the second vanishes); accept only a host directory (costs: the twin may not be able to tell the kinds apart reliably); accept any mount and rely on the launcher to have made the right one (costs: a hand-started container is unchecked in the way that matters). Also: must the twin check that the directory is **writable** by the twin's user? A test write of a marker file that it then removes would show it, and would leave a stray file if the twin is killed between the write and the removal, which the person would then find in their directory. And what, if anything, it checks about who will own the files on the host (D6). Not chosen.
- **V4. How it verifies on each host.** The principal said the method may vary by host. What is known is general knowledge and was not tried or taken from a repository file: on a Linux host the mount table inside the container shows a bind mount; on macOS and Windows the container runs inside a virtual machine, and a host directory appears as a file-sharing mount whose type and appearance in the mount table differ. So the check has to be written and tried per host, and its result may be wrong in either direction (a mapped directory reported as unmapped, which blocks a good run; an unmapped one reported as mapped, which is the silent loss). **Open: which host operating systems the twin must be verified on.** No design is offered here.
- **V5. When "as soon as possible" is, and what happens later.** At the twin's start, before it accepts any command or begins any session, and before anything is written to the working file: to confirm that this is the meaning. And if the mapping disappears during a run (a host directory removed, a share disconnected), the twin cannot fix that either. Options: refuse further saves and tell the person, keeping the session running; or stop as at start. Not decided.
- **V6. Where the message appears, and in what words.** In the page, in the container's log, or both (an exit, V1 (a), leaves only the log and whatever the launcher shows). Text shown to a person is a locale key and never text in code (`CLAUDE.md` §17: a key in all eleven locale files). What to do differs by host, since it is how to start the launcher there, so a text per host is a consequence. No text is written here. Whether a message in a container's log or a launcher's own window falls under §17 as the app's screens do is a question for the localisation owner.
- **V7. The launcher's default host directory.** Where it is created is a convention per host operating system. Candidates, none chosen, each to be checked against that system's own guidance for where a program keeps a user's documents or data: a folder under the user's documents directory (visible, where a person would look for files they kept); a folder under the per-user application-data directory (out of the way, harder to find); a folder beside the launcher. Its permissions: owner-only would match the working file, and interacts with D6, the owner of files the container creates there. If the launcher cannot create it, it must not start the container: stated for confirmation, as it follows from "always present". On the next launch the directory already exists and is reused, so files from earlier runs are in it; that is where the expiry offer finds the expired copies it lists.

- **D4. Where the twin's list of its saved copies lives** (R1). An index kept inside the container is lost when the container is removed, and a new container's index knows nothing of the files already in the mapped directory. An index kept in the mapped directory itself travels with the files. Costs of the second: it is a file in a directory the person can see, edit and delete, so it cannot be trusted more than a scan and has to be checked against the files; it holds the names of saved copies, which contain a pseudonymous id and a timestamp, and nothing else. A third way is no index at all in a container: scan the fixed directory, which is the only place saved copies can be (R1 option (b), which loses its main cost when there is only one directory).
- **D5. The remembered directory** (question F of `oi-simfw-05-saved-file.md`). In a container the host directory is known only on the host: to the launcher, or in the command the person types. The twin inside the container sees only the fixed path and can remember nothing about the host path. So "the twin remembers the directory" can only be done, for a container, by something on the host. Where it is kept there is the question.
- **D6. Permissions on the mapped directory** (C4) stay open, now for a fixed path: the owner and mode of a saved copy as seen from the host, and the user id the twin runs as in the container.

- **C1. A running container cannot gain a mount.** A directory is mapped when a container is started, not afterwards. (This is how container runtimes generally work; it is not from a repository file.) So the principal's earlier direction, that the person picks the directory and the twin remembers it, cannot mean picking any host directory while the twin runs inside a container.
  - **(a) The mapped directory is fixed at launch.** At save time the person chooses only a subdirectory or a name inside it, and the remembered default is the launch setting. Costs: a different directory means stopping and starting the twin, and the working session is lost with it unless it was saved first. Gains: needs nothing that does not exist.
  - **(b) A host-side launcher asks for the directory and starts the container with that mapping, and remembers it** (question D of `oi-simfw-05-saved-file.md`; not designed, not built). Costs: needs the launcher. Gains: picking a directory works as the direction describes, before the session starts.
  - **(c) Both:** the launcher sets the mapping, and inside it the person may choose a subdirectory or a name.
- **C2. A save when no directory is mapped.** A save into the container's own storage vanishes when the container is removed. That is the silent loss of something the person asked to keep. Options: refuse the save and say why; save inside the container with a clear warning that the copy will not be kept; or ask the person to restart with a mapping. Not chosen. Whichever it is, the person is told; a save that appears to succeed and is later gone is the one outcome to rule out, and that much is offered for confirmation.

Permissions on a mapped directory.** A file the container's user creates in a host directory may belong to a different user id on the host, so an owner-only (0600) file could be unreadable by the person who wants to examine it. Not decided.
- **C6. The working temporary file stays inside the container** (Q1 option A: the container's own temporary directory; Q2: unlinked while open where the host allows it) **and is gone with it.** That is the intended consequence of Q1 and Q2 together with this answer: only a saved copy reaches the mapped directory.
