## 1. What this draft is, and is not

#566 asks for a decision record: the supported providers, the common interface, the per-provider mapping against the
storage an individual has, a verified conditional-write result for each, the build-or-adopt decision, a contract-test
plan, and SOUP records for anything adopted. **This draft holds the research so far (task B of the issue). It decides
nothing.** It is not the decision record.

**How the evidence is graded.** Rev 1 rested on search excerpts. **Rev 2 (2026-10-27) reads the provider pages first-hand**
(downloaded 2026-10-27 and converted to text; the page's own "last updated" date is given where the page shows one).

| Grade | Meaning |
|-------|---------|
| **Read** | The provider's own page was read on 2026-10-27 and says so. |
| **Excerpt** | A search result quoted an official page that was not read. |
| **Unverified** | General knowledge, an inference, or nothing found on the pages read. |

`SWR-MG-11` requires the result "verified against the provider's current documentation and recorded with the date".
**A "Read" row meets that for what it states. It is documentation, not a test:** a provider's page does not prove the
behaviour, and the contract tests (two simultaneous claim writes) are still owed per provider (§5).

## 2. The interface already in the repository

The common API is, in effect, written. `common/npps-core/src/object_route.rs` defines six object calls on named
objects; a provider implements only these (`SWR-MG-11`):

| Call | Meaning |
|------|---------|
| `objectGet(name)` | the object, or null when there is none |
| `objectPut(name, data)` | write, replacing any earlier object |
| `objectCreate(name, data)` | write **if and only if** no such object exists, arbitrated by the store itself (`SWR-MG-07`) |
| `objectDelete(name)` | true also when there was no such object |
| `objectList(prefix)` | names under a prefix |
| `objectSpace()` | free bytes, or null when the provider cannot say |

Any call may return `{failed: true}`; a flow then ends `route_unavailable`. The core fixes the object names
(`np-migration-bundle.npbk`, `np-migration-claim.json`, `np-migration-confirmation.json`, probe prefix `np-probe-`) and
holds the claim, read-back and probe logic. The Kotlin, Swift, C# and TypeScript `ObjectStore` drivers are named; **no
provider is implemented in any of them.**

### 2.1 The issue's list against the six calls

| #566 item | Covered by | Note |
|-----------|-----------|------|
| 1. Put and get the bundle | `objectPut`, `objectGet` | **Gap 1:** one call carries the whole bundle as a hex string. No chunked or resumable put. |
| 2. Find the bundle | `objectGet` by fixed name, `objectList` | Covered. |
| 3. Claim, read the claim | `objectCreate`, `objectGet` | Covered. |
| 4. Write and read the confirmation | `objectPut`, `objectGet` | Covered. The confirmation is an unconditional replace. |
| 5. Release a claim | `objectDelete` | Covered. |
| 6. Delete the bundle | `objectDelete` | Covered. Whether the process deletes it is not decided. |
| 7. Read-after-write per provider | none | **Gap 3:** not an interface matter; it belongs in the decision record (§3). |
| 8. Authentication on the user's own account | none | **Gap 2:** the host handles it; the interface has one undifferentiated `failed`. |
| 9. All four app targets, cross-platform bundle | one driver per language | **Gap 5:** where the adapters live is unstated. |
| M12 space check | `objectSpace` | Covered. |

### 2.2 Gaps and questions raised

1. **Large bundles.** `objectPut` and `objectCreate` take the whole payload as one hex string, which doubles its size in
   memory, and there is no chunked or resumable upload. The issue says "resumable or chunked if a provider needs it".
   Bundle size is not stated in the documents read. Graph needs byte ranges in multiples of 320 KiB and recommends resumable
   upload above 10 MiB (§3.2). This needs a decision and probably a change to `object_route.rs` or a
   driver-side chunking rule.
2. **Sign-in failure cannot be told from other failure.** No network, no permission, a refused write and a signed-out
   account all return `{failed: true}`. M12 asks the message to say which operation failed *and what the user can do*
   ("sign in again"). Whether the probe result can carry a reason is open.
3. **Consistency is assumed, not stated.** After `createClaim` the flow reads the claim back and checks it is ours
   (`claim_readback`). `OI-UI-KMP-11` M9 (3) says write-then-read-back narrows the race and does not close it on an
   eventually consistent store. Each provider's read-after-write for get after create, put and delete must be written down
   before the claim is called atomic on it.
4. **Name-based get and create may not exist on every consumer store.** The core addresses objects by fixed name. Google
   Drive's own reference says a name "isn't necessarily unique within a folder", so "get by name" is a query and "create if
   absent by name" has no native form (**confirmed**, §3.2). A client-chosen file ID might serve; whether a repeated create
   is refused is **not stated** on the pages read. This is the largest risk to the consumer-account mappings.
5. **Where the adapters live.** Four driver languages are named; CLAUDE.md §20 says the UI is written once in Compose
   Multiplatform. Whether provider adapters are written once in shared Kotlin or once per platform is unstated, and it drives
   the cost of keeping up that #566 asks about.
6. **`objectCreate` has two outcomes and the providers have more.** The core's `{created}` is true or false, and any call may
   be `{failed}`. S3 can answer **409** when a concurrent delete wins (retry for a PutObject, restart for a multipart
   upload), OneDrive reports a name conflict only at the end of an upload session, and a lost response leaves a claim
   that may or may not have been written. The mapping from each provider's answers to created, already exists and
   indeterminate has to be defined, because the flow treats a claim "written but not read back" as not owned
   (`SWR-MG-07`).

**Google Drive, conditional create.** The files reference (last updated 2026-07-14) says a file's name "isn't necessarily
unique within a folder", which **confirms Gap 4**: there is no create-if-absent by name. `files.generateIds` produces IDs
"which can be provided in create or copy requests". Neither the files resource nor the create page read shows an ETag or a
precondition parameter, and **whether a second create with an already-used ID is refused is not stated** on the pages
read. A client-chosen ID is the only candidate for an atomic claim on Drive and it is **Unverified**.

**OneDrive, conditional create.** The `createUploadSession` page (last updated 2025-10-15): `@microsoft.graph.conflictBehavior`
is `fail` (default), `replace` or `rename`; an `if-match` ETag that does not match returns 412, and an `if-none-match` ETag
that matches returns 412. A conflict that arises during an upload session is reported **only when the last byte range is
uploaded**, as `409 Conflict` with code `nameAlreadyExists`. Byte ranges must be multiples of 320 KiB (327,680 bytes),
resumable upload is recommended above 10 MiB, and an explicit completion step (`deferCommit`) is supported only on OneDrive
for Business and SharePoint. **Not read:** a simple (single-request) upload with `conflictBehavior`, and any consistency
statement.

### 3.3 Reaching a provider from every target

`OI-UI-KMP-11` M10 (d) says "Android to iOS rules out any provider that is not usable on both". The CloudKit Web
Services reference (Documentation Archive) says CloudKit web services and CloudKit JS let an app reach its CloudKit
databases from the web. **How the private database is reached from a non-Apple native app, what sign-in it needs, and
whether the archive page is current were not examined.** The Apple route stays open for Android until that is read. The
other four providers are plain HTTPS services reachable from any target.

## 4. What this suggests (not decided)

1. AWS and Oracle Cloud probably offer an individual no storage without an infrastructure account. This is still
   **Unverified**; if confirmed, the issue's own finding applies: the user creates one, or the provider is listed as not
   supporting consumer accounts.
2. The four infrastructure object stores each document a create-if-absent (S3 `If-None-Match: *`, Blob `If-None-Match: *`,
   Cloud Storage `ifGenerationMatch=0`, OCI `if_none_match`), and S3, Cloud Storage and OCI document strong consistency.
   Azure's consistency and OCI's failure code and concurrency behaviour are the open items.
3. The consumer routes differ. OneDrive has a documented `fail` conflict behaviour, with the drawbacks in Gap 6 and an app
   folder the user can alter. CloudKit documents `create` only in its web-services form. Google Drive has no documented
   create-if-absent by name, so it depends on a client-chosen ID that nothing read confirms.
4. A provider without a usable conditional write is not offered for migration and stays listed for UHDR-only backup
   (`SWR-MG-10`, M12 as confirmed 2026-10-09). The in-app check is a capability check, not a proof of claim safety under two
   simultaneous writers (`SWR-MG-12`).

## 4a. Build or adopt

**Status: evaluated, not decided.** The decision is the principal's. Nothing here adopts a library, so no SOUP record is made
(`NP-SOUP-RUST-001` and `NP-SOUP-KOTLIN-001` are where one would go).

### 4a.1 What a candidate must pass

From the issue and from the standing rules (`CLAUDE.md` §22; `NP-SOUP-KOTLIN-001` §2a):

1. It exposes the **conditional create**. The issue: "a library that does not expose the conditional write is not enough".
2. It runs on **every app target**: Android, iOS, desktop and web (`CLAUDE.md` §20).
3. Its licence does not oblige NeurOne's code to be copyleft (§22; §2a rule 5).
4. It is not a pre-release (§2a rule 2), and it is not used for cryptographic work that §22 gives to the Rust core.
5. It would need a SOUP record (IEC 62304), and it covers providers the app offers.

### 4a.3 What the evidence supports

1. **No candidate covers the five providers.** OpenDAL and `object_store` expose a conditional create for the three
   infrastructure stores they share with the issue's list (S3, Cloud Storage, Azure Blob). Neither covers OCI natively, and
   neither gives a create-if-absent for OneDrive, Google Drive or CloudKit, which are the consumer routes the issue most
   cares about. **A library does not remove the per-provider work for the hardest rows.**
2. **jclouds and rclone fail the issue's own tests.** jclouds exposes no conditional write and is JVM-only. rclone offers no
   shown atomic create and is a Go runtime to embed.
3. **Adopting a Rust library does not fit `npps-core` as it stands.** The core does no network input or output: a host
   answers the six object calls, and the crate asks for no entropy (`object_route.rs`; the `getrandom` note in its
   `Cargo.toml`). OpenDAL or `object_store` would bring a `reqwest` transport. It would have to be a separate crate behind the
   same six calls, as `btle-jni` is, not part of the core. That is a placement decision for the principal.
4. **Some of what a thin adapter needs is cryptography.** S3 request signing is HMAC-SHA256, which `CLAUDE.md` §22 puts in the
   Rust core (which already depends on `hmac` and `sha2`). Not a reason to adopt a library, but a reason not to write it in
   Kotlin.
5. **The interface is smaller than any candidate's surface.** The six calls are a subset of what OpenDAL and `object_store`
   do, which supports the issue's own suspicion that "building thin adapters may be cheaper than adopting a large library".
   **This draft does not show it is cheaper**, because the cost of the dependencies was not measured (4a.5).
6. **Sign-in is not in any candidate.** Google and Microsoft sign-in, and the iCloud account for CloudKit, are the platform's
   and the host's. The issue's item 8 stays whichever route is chosen.

### 4a.4 Cost of keeping up

The provider contract suite (`SWR-MG-11`) is the same under every route, so it is not a difference between them. What
differs is who tracks provider changes. With thin adapters NeurOne does, for five providers. With OpenDAL or `object_store`
the library tracks three infrastructure providers and NeurOne still tracks OCI, OneDrive, Drive and CloudKit, and each
upgrade of a pre-1.0 library (`opendal` is 0.59.5) is a SOUP change with its anomaly evaluation.

### 4a.5 Measurements (2026-10-27)

**Findings.**

1. **Both configurations pull a C cryptography library.** `aws-lc-rs` 1.18.2 and `aws-lc-sys` 0.46.0 (through `rustls`) are in
   both trees, with `hmac`, `sha1`/`sha2` and `md-5` additionally in `od`. The repository has none of this today. This meets
   `CLAUDE.md` §22 head-on ("not taken from a platform or third-party library"), though the core already depends on the
   RustCrypto crates. **Whether a TLS transport counts as the "cryptographic" work §22 means is for the principal.**
2. **`opendal` with Azure carries RUSTSEC-2023-0071** (`rsa` 0.9.10, "Marvin Attack: potential key recovery through timing
   sidechannels", **no fixed upgrade available**), through `reqsign-azure-storage` and `opendal-service-azblob`. Whether the
   Azure path the app would use ever performs an RSA private-key operation was not examined. The `object_store` build
   has no advisory.
3. **Neither full configuration builds for iOS or Android on this host.** `cargo check` for `aarch64-apple-ios` and
   `aarch64-linux-android` stops in `aws-lc-sys`'s build script, because the Apple SDK and the Android NDK are not installed
   here. **That is not evidence the build is impossible with them.** It does show a C toolchain per mobile target is needed.
4. **Web.** `od` with the transport fails on `wasm32-unknown-unknown` at `getrandom`; `os` fails on Tokio and `aws-lc-rs`
   (its README says the same). Part of that is the probe's own Tokio features, so these two are **inconclusive for OpenDAL**
   and **consistent with the README for `object_store`**.
5. **The same OpenDAL core with the S3 service and no transport checks clean on every target.** A fourth throwaway crate with
   only `services-s3` and `default-features = false` (no `reqwest`, no TLS) ran `cargo check` clean for
   `wasm32-unknown-unknown`, `aarch64-apple-ios` and `aarch64-linux-android`; 103 crates; no `aws-lc`, `rustls` or `reqwest`
   (it keeps `hmac`, `sha1`, `sha2`, `md-5`); `cargo-audit` found no vulnerability. **That it type-checks is all this shows.**
   It was not run, a host-supplied transport was not wired, and the Google Cloud Storage and Azure services were not
   added to this variant.

6. **A host-supplied transport works, against a stand-in.** OpenDAL 0.59.5 has a seam for it: the trait `HttpTransport`
   (`fetch(Request<Buffer>) -> Response<HttpBody>`), installed on an operator with
   `with_context(OperationContext::new().with_http_transport(...))`. A fifth throwaway crate, `odt`, builds OpenDAL with only
   `services-s3` (no `reqwest`, no TLS, **0** of `aws-lc`, `rustls`, `reqwest`, `hyper`, `ring`; 104 crates; `cargo-audit` found
   no vulnerability), and supplies a transport that is an **in-memory object store written for the probe** and does not
   speak to any provider. Against it:

   | Step | Result |
   |------|--------|
   | First create-if-absent of `np-migration-claim.json` | succeeded |
   | Second create of the same name | refused; OpenDAL reports `ConditionNotMatch` |
   | Read back | the first writer's bytes |
   | Read of a missing name | `NotFound` |
   | List by the prefix `np-` | the one object |
   | Two concurrent creates of one name | exactly one succeeded |
   | Delete, then stat | `NotFound` |
   | Requests the transport saw | `PUT` with `If-None-Match: *` for both creates |

   The binary is 2.65 MB (same profile as 4a.5; 2.25 MB over `base`), and `cargo check` for `aarch64-apple-ios` and
   `aarch64-linux-android` is clean. **What this shows:** OpenDAL sends the conditional header that the S3 documentation
   calls for (§3.1), turns a 412 into a distinct error, and needs nothing from the host but the transport, so no TLS stack
   has to join the Rust core. **What it does not show:** that S3 or any provider answers as the stand-in does (the stand-in
   is mine, and its serialising lock is why exactly one concurrent create won, not S3's arbitration); that the 409 and
   indeterminate cases of Gap 6 are handled; that the transport can be implemented by Kotlin or Swift across the C ABI
   (a callback into a platform HTTP stack was not built); or the web target (the probe's Tokio entry point was not checked
   for `wasm32`). The stand-in needed a `LastModified` and `ETag` in its list reply before OpenDAL would parse it, so a real
   adapter must reproduce provider replies fully.

**Still not measured:** the app-size effect on a device (iOS, Android, web); a run against any provider; a platform
(Kotlin or Swift) implementation of the transport behind the C ABI; the licences and targets of the Azure, Google, OCI, Graph and CloudKit SDKs; and whether
OCI's S3-compatible endpoint honours `If-None-Match: *` (OCI's "Amazon S3 Compatibility API" page, read 2026-10-27, says
nothing about conditional writes either way).

**AWS SDK for Kotlin.** Its targets page (read 2026-10-27) lists JVM, Android (API 24+) and GraalVM; no iOS and no web. Its
licence is Apache-2.0 (the repository `LICENSE`).

### 4a.6 Leading option (not decided)

Thin adapters per provider behind the existing six calls, because only that route reaches all five providers and the
consumer routes. The measurements change what a library spike would look like: a full OpenDAL or `object_store` build adds
3.3 to 4.4 MB on the host, a C cryptography library the repository does not have, and a mobile C toolchain, and OpenDAL with
Azure carries an advisory with no fix. **The one variant that checked clean everywhere is OpenDAL's core without a transport
(4a.5 items 5 and 6).** If the principal wants a library for the three infrastructure stores, that variant, with the
transport supplied by the host so no TLS stack joins the core, is the one worth a spike. Its seam works against a stand-in
(item 6); the open steps are a platform transport behind the C ABI and a run against a real provider.

## 4b. The thin-adapter library (built)

**Direction (principal, 2026-10-27):** build the thin adapters as a reusable library. This is the first slice. It is code,
and it is tested only against a stand-in for the provider (below), so it verifies the adapter and nothing about any provider.

**Why this is thin and reusable.** An adapter is one class over `HttpTransport` and an `AccessToken`; it holds no sign-in, no
signing and no state. The same class runs on every target that has a transport. The contract suite is what makes a new
provider cheap to add and safe to compare: the claim test (exactly one of 24 simultaneous creates wins) and the
absent-versus-error rules run unchanged against it.

### 4b.2 How it answers the gaps

- **Gap 6 (create outcomes).** The interface already has two outcomes and an exception: `true` (created), `false` (the object
  exists) and a thrown `CloudStoreException` for everything else, including no answer. The adapter never turns an unmapped status
  or a lost reply into `false`, so the flow treats it as "route unavailable" and the claim is not assumed written or refused.
  Providers' extra cases (S3's 409, OneDrive's late conflict) are thrown, not retried, until a decision says otherwise.
- **Gap 2 (sign-in vs other failure).** `CloudStoreException.status` carries the HTTP status (401 for a refused token), so a host
  can tell a sign-in failure from the rest, and `CloudAuthException` (§4c) is a `CloudStoreException` with status 401 for a sign-in that is needed, so the same handling covers both. The core's probe still sees one `failed`; passing the reason through is not done.
- **Gap 5 (where adapters live).** In `common/cloudstore`, a Kotlin Multiplatform module (JVM, wasmJs, iOS arm64 and simulator)
  that `:core` depends on, so the Android app and the shared Compose app reach it and neither app's tree holds it. The package names
  are unchanged (`life.neurone.core.*`), so no caller changed. The Swift and C# apps have their own driver interfaces and would
  need their own adapters. **Swift: the native CloudKit adapter is written** (Rev 13); the other providers have none in Swift (the Swift app could reach them through the iOS build of this module, which is not wired), and C# and TypeScript have none.
- **Gap 1 (large bundles).** Not addressed. `put` sends the whole array in one request.

### 4b.3 What changed in shipped code

`HttpTransport` (with `HttpRequest` and `HttpResponse`) and the `ObjectStore` interface moved out of `app/android/core` into `common/cloudstore`, because the library needs them and `common/` imports nothing outside `common/`. `:core` re-exports the module with `api(project(":cloudstore"))`; `.github/workflows/desktop-package.yml` also triggers on `common/cloudstore/**`. **Code other apps use still sits in `app/android/core`** (the rest of `:core`); this change moves only what the cloud library needs and does not relocate it.

`HttpRequest.method` was honoured as GET or POST only by the OkHttp and JDK transports (the iOS one already passed the method
through). Both now pass any method through, with no body for GET and HEAD, because the object stores need DELETE. The GET and
POST paths behave as before. **These two transport edits are not covered by a test.** The moved module's 12 tests and 99 of `:core`'s migration, analytics and OTA tests passed after the move (2026-10-27); the iOS, wasmJs and Android-app builds were not run.

### 4b.4 What is not done

- **No run against Google.** `FakeGcs` is written from the documentation (§3.1, §3.2): 412 for a repeated
  `ifGenerationMatch=0`, 404 for a missing object, a paged list. It is not Google. The requirement's own test is "a contract
  test suite run against each provider" (`SWR-MG-11`); that part, declared as `SWR-MG-11#contract`, has **no test**.
- **No run against Azure.** `FakeAzureBlob` is written from Microsoft's REST reference (Put Blob 201, Get Blob 404, Delete
  Blob 202, List Blobs XML with `NextMarker`); it is not Azure. Not covered: which of 412 and 409 a real account answers
  for `If-None-Match: *` on an existing blob (both are read as "exists"), Entra token acquisition for the resource
  `https://storage.azure.com/`, Shared Key and SAS, and blobs larger than the documented single-call maximum of 5,000 MiB
  (a larger body is a 413, which the adapter throws; this is Gap 1 for Azure).
- **No run against S3.** `FakeS3` is written from Amazon's API reference (PutObject 200, `If-None-Match: *` on an existing key 412,
  GetObject 404, DeleteObject 204, ListObjectsV2 XML with a continuation token); it checks that the condition and every `x-amz-*`
  header is among the *signed* headers, but it does **not** verify the signature, which is the core's, checked against Amazon's
  examples. Not covered: the credentials (the person's AWS access key and secret, or temporary ones), where the host keeps them,
  a bucket with dots (use path-style), the 403-for-a-missing-key behaviour when the credentials cannot list the bucket (read as a
  refusal), the single-PutObject size limit (not checked here; Gap 1), and **an S3-compatible store that ignores `If-None-Match`
  and overwrites**: only AWS S3 is documented to honour it, and the capability check (`SWR-MG-12`) is what catches the others.
- **No run against OneDrive.** `FakeOneDrive` is written from the Graph pages (§3.1). It serialises racing sessions, so it cannot show that OneDrive arbitrates them: the documentation does not say it does, and the contract test against a real account (`SWR-MG-11#contract`) is what would. Not checked: the reserved names, the personal-versus-business differences (`deferCommit`), throttling (429 with `Retry-After` is thrown, not retried), and that a deleted claim in the recycle bin does not block a new one with the same name.
- **No run against CloudKit, and the pages are old.** `FakeCloudKit` is written from the CloudKit Web Services pages in Apple's Documentation Archive ("Updated: 2016-06-13"); whether they match the service today was not established. Not known: whether two simultaneous `create`s are arbitrated atomically; **a query can miss a record just written** (the page says indexes update asynchronously) and the container schema must make `recordName` queryable and define `NpObject` with an Asset field `data` (a development schema is deployed to production by the owner); where in a reply the rotated web authentication token comes (the page says one "is provided in the response"; the adapter hands the host a top-level `ckWebAuthToken` and that is a guess); the record-name rules and the `${f}` download placeholder (UC-110, from memory); the iCloud quota (413 `QUOTA_EXCEEDED` is thrown). The native CloudKit route for iOS is a Swift adapter, not this one.
- **No run against Google Drive.** `FakeDrive` is written from the Drive API pages (§3.1, read 2026-10-28). It lists a write at once; **whether Drive's listing is current after a write is not stated on the pages read**, so a quick second `put` could create a duplicate (reads and writes then follow the newest). Not examined: whether Drive accepts a client-chosen file ID that did not come from `generateIds` (the adapter does not rely on it, and if it does, a name-derived ID might still not give an atomic create); the app-folder size and rate limits; the per-request cost of finding a file by name.
- **No other provider.** The five providers named in the issue now have an adapter, and the Drive one cannot claim (Gap 4).
- **Sign-in is a library with no caller** (§4c). `:cloudstore` still takes an `AccessToken` from its host; `common/cloudauth` is what obtains it, and nothing in an app constructs it yet.
- **Wired in for three.** The backup route (§4c.9) builds the Google Drive, OneDrive and iCloud adapters for a signed-in account. No screen or flow constructs a `GcsObjectStore`, an `AzureBlobObjectStore` or an `S3ObjectStore`: they also need a bucket, container or region typed in and kept.
- **The Swift, C# and TypeScript drivers** have no adapters.

## 4c. Sign-in and credential storage (built, no caller)

**Direction (the principal, 2026-10-28):** one shared library that signs in to every supported provider and keeps the result, tested against fakes; the platform launchers and screens come later, and client registrations are supplied by the host.

### 4c.1 What exists

`common/cloudauth` (Gradle `:cloudauth`, package `life.neurone.core.cloudauth`) depends on `:core` and `:cloudstore`; neither depends on it. Requirement: `SWR-MG-19` in `docs/np_sw_001.md`.

| Provider | Sign-in | What is kept | Refresh | Sign-out |
|----------|---------|--------------|---------|----------|
| Google (Drive, Cloud Storage) | Authorization code + PKCE (S256), system browser; one grant per service (installed apps have no incremental grant); no identity scope is requested | Access token and expiry, refresh token | Refresh-token grant; refusal (`invalid_grant`) means sign in again | Revoke call, then delete |
| Microsoft (OneDrive, Azure Blob) | Same flow; tenant `consumers` for OneDrive (`Files.ReadWrite.AppFolder offline_access`), `organizations` for Azure (`https://storage.azure.com/user_impersonation offline_access`) | Same | The refresh token is **rotated** on each refresh and the new one replaces the old | Delete only (no revoke call used) |
| Apple (CloudKit Web Services) | The container's sign-in page, reached through the 421 reply's `redirectURL`; the callback carries `ckWebAuthToken` | The token, as received (a `+` stays a `+`) | A token serves one round trip; the service returns a new one and `cloudKitTokenSink` stores it | Delete only |
| AWS (S3) | None: `addAwsKeys` takes the person's keys, checked for blanks, whitespace and control characters | Key id, secret, optional session token and expiry | Temporary keys expire; no refresh | Delete only |

**Storage.** All credentials are one JSON value under `np.cloud.accounts` in the host's protected `KeyValueStore`, so the host's `EncryptedKeyValueStore` seals it (`SWR-MG-16`). The key is `perInstall` in `common/npps/migration-keys.json`: a credential belongs to an install and never moves in a migration (`SWR-MG-01`). A stored value that cannot be read fails with `STORE_UNREADABLE` and is never overwritten. `check-migration-keys.ts` now scans `common/cloudauth`, or the entry would read as stale.

**Seams.** `AuthorizationLauncher` (open this URL in the system browser, return the redirect URL) is the one thing each platform implements. `CloudAuthConfig` carries the client identifiers and redirect URIs; none is in the source, and an unconfigured provider fails with `NOT_CONFIGURED` naming it. SHA-256 and random bytes are the Rust core's (`CLAUDE.md` §22). Refresh is serialised: any number of callers make one request.

**Errors.** `CloudAuthException` extends `CloudStoreException`; `SIGN_IN_REQUIRED` carries status 401, and `CloudAuth.needsSignIn(e)` is true for it and for a 401 or CloudKit 421 from an adapter. A refresh that gets **no answer** is `NETWORK` and does not mark the account as signed out. Tokens are never put in a message.

### 4c.2 What is not done

- **No screen, no caller.** Nothing in an app constructs `CloudAuth`. The Android (§4c.3), iOS (§4c.4) and desktop (§4c.5) launchers are written; the web launcher (§4c.6) opens the sign-in but cannot finish it, as is the provider-picker UI with its strings (`CLAUDE.md` §17).
- **No client registration.** A Google, Microsoft and CloudKit client must be registered by the owner, with a redirect URI each platform can receive (a custom scheme or loopback address); store review and Google's verification for the `drive.appdata` scope are not examined.
- **No run against a provider.** The fakes are written from the providers' pages. Not known: Microsoft's and Google's exact refusal codes beyond `invalid_grant`, `interaction_required`, `consent_required` and `login_required`; where in a CloudKit reply the rotated token arrives; what a consumer Microsoft account does with `scope` on refresh. The PKCE challenge is checked against RFC 7636 Appendix B.
- **Oracle Cloud** has no sign-in here and no adapter.
- Three constants have no derivation (UC-112, UC-113, UC-114).

### 4c.3 The Android launcher

`ExternalBrowserLauncher` (`common/cloudauth`) is the logic that any host with "open the browser, get an address back from the system" shares: it opens the address through a function the host gives it, waits, and takes only an address that is the registered redirect (the same scheme, host and path, followed by nothing, `/`, `?` or `#`). The Android parts are thin: `AndroidBrowser.open` (an `ACTION_VIEW` intent for an `https` address, so the person's own browser and not a web view, RFC 8252), `NeurOneApplication.browserLauncher`, and `MainActivity`, which reports the intent that returns (`onCreate`, `onNewIntent`) and its own `onPause` and `onResume`. **The browser cannot say it was closed**, so an app that comes back to the front without an answer cancels the sign-in; this relies on Android delivering the redirect before `onResume`, and a pause that is not the browser (a system dialog) cancels it too.

The redirect scheme is a build input: `manifestPlaceholders["cloudAuthRedirectScheme"]`, from `-PcloudAuthRedirectScheme=` and defaulting to `life.neurone.app.oauth`. **A custom scheme can be claimed by another app**; nothing here trusts the answer for that reason, and `state` and the PKCE verifier decide it (§4c.1). Whether a provider accepts that scheme for an Android client is a registration question (Google's Android clients expect a scheme derived from the client ID; Microsoft's want the redirect registered in the portal): the scheme and the registrations have to agree, and neither exists yet. If a provider needs a different scheme from another, the manifest needs a second filter, which this change does not add.

Tested: the six `ExternalBrowserLauncherTests` on the JVM. **Not compiled and not run:** the Android parts. The session had no Android SDK. Not exercised on a device: the browser opening, the intent returning, the order of `onNewIntent` and `onResume`, a process killed while the person is in the browser (the waiting sign-in is lost and the person starts again), and a phone with no browser (the open fails and the launcher reports `PROVIDER`).

### 4c.4 The iOS launcher

`IosAuthorizationLauncher` (`:shared`, `iosMain`) opens the sign-in in an `ASWebAuthenticationSession`: the person's own Safari sign-in in a sheet the app cannot read, which returns only the address it was sent to. The session catches a custom-scheme redirect without the app registering the scheme, so `Info.plist` is unchanged. `WebSessionRules` (`common/cloudauth`) decides what is not platform: the scheme to watch for, and what a finished session means (an address is the answer; the documented "cancelled login" error is `CANCELLED`; anything else is a failure that does not quote the platform's message, which can carry the address and so the code).

**An `https` redirect is refused**, with a reason, before the sheet opens. Matching an `https` callback needs the session's newer callback form (iOS 17.4), which this launcher does not use. That rules out CloudKit's sign-in callback as written (`CloudKitConfig.signInCallbackUri` is an `https` address) until either the form is added or the container's callback is a custom scheme; which of the two is open, and no CloudKit container is registered either.

Tested: the two `WebSessionRulesTests` on the JVM. **Not compiled and not run:** the Kotlin/Native class. The session had no Mac. In particular the generated binding names (`ASWebAuthenticationSession`'s initialiser and `presentationContextProvider`) were written from memory of the Kotlin/Native bindings. The Swift app (`app/ios/NeurOne`) does not use `:cloudauth`.

### 4c.5 The desktop launcher

`LoopbackAuthorizationLauncher` (`common/cloudauth`, JVM) is the loopback redirect of RFC 8252 section 7.3: the browser is sent to the provider and the provider sends it back to `http://127.0.0.1:<port>/...`, where a listener bound to `127.0.0.1` only is waiting for as long as the sign-in waits. The browser is opened after the listener is up. It answers only a `GET` for the redirect's path whose `Host` is the loopback address and port, so a page that points its own name at this address is refused (DNS rebinding); the browser's request for an icon and anything else gets an error and the wait carries on. The first matching request is the answer, handed back whole (a code, or `error=access_denied`) for `CloudAuth` to decide. A request head over 8 KiB is refused (UC-114). Cancelling the wait closes the listener and every connection. What the browser is shown afterwards is the host's text (`donePage`), empty by default, because it is text the person reads (`CLAUDE.md` §17).

**The port is the one in the registered redirect**, so it must be free: a port in use fails the sign-in with a reason and nothing opens. A provider that accepts any loopback port would let a free one be chosen, but `CloudAuth` sends one redirect address in both the sign-in and the token request, and they have to agree; choosing a port per sign-in would need `CloudAuth` to take the address from the launcher. Not done. Google's desktop clients and Microsoft's public clients accept a loopback address; whether each accepts the chosen fixed port as registered is part of the registrations, which do not exist.

`DesktopBrowser` (`:desktop`) opens the sign-in page with `open` (macOS), `rundll32 url.dll,FileProtocolHandler` (Windows) or `xdg-open` (Linux and the rest), as an argument list and never through a shell, for an `https` address only. `DesktopBrowser.launcher(donePage)` puts the two together; nothing calls it yet.

Tested: seven tests of the listener on the JVM with real sockets on `127.0.0.1` (the answer and the page, the refused requests, the oversized request, a busy port, a browser that will not open, cancellation) and two of the commands. **Not run:** on macOS or Windows, with a real browser, or against a provider; a firewall that prompts for a listener is untested; `xdg-open` with no desktop (a server, a container) fails and is reported as the browser not opening. The `:desktop:test` run here skipped the Bluetooth JNI build, which needs system libraries this session lacks.

### 4c.6 The web launcher

`WebAuthorizationLauncher` (`:web`, `wasmJsMain`) opens the provider's page in a small window of the person's own browser (`window.open`). The provider sends that window back to `oauth-callback.html`, a page of the app's own origin with one script and a Content-Security-Policy of its own (`default-src 'none'; script-src 'self'`). The script posts its address to the app's page over a `BroadcastChannel`, takes the answer out of its history and closes the window; the wait ends when `ExternalBrowserLauncher` takes an address that is the registered redirect. A `BroadcastChannel` and not `window.opener`, because a provider's page may set `Cross-Origin-Opener-Policy`, which severs the opener, and the channel reaches only pages of the same origin. A redirect of the whole page is not possible: the web app keeps nothing in the browser (`REQ-SW03-18` (b)), so the sign-in's own state would be lost.

Limits of the launcher itself. A browser opens a window only for a script started by a click, for a few seconds afterwards: a sign-in must start from the person's tap, and CloudKit's, which asks the network first, may be refused (reported, not retried). A closed window is not noticed, because `window.closed` can read true at once after a provider sets that policy; the screen's `cancel()` or the coroutine's cancellation ends the wait. The window keeps its opener, because `noopener` makes `window.open` return null and a blocked window could not then be told. The registered redirect must be `<origin>/oauth-callback.html` of the page that asks.

**A web sign-in cannot complete yet, for three reasons that are outside the launcher.**
1. **The web app has no HTTP transport** (`PlatformServices.httpTransport` is null there), so `CloudAuth` and the adapters have nothing to send a request with.
2. **The page's Content-Security-Policy is `connect-src 'self'`** (privacy review Finding 1), which refuses the providers' token and storage hosts. Widening it is a decision for that review, not a detail of this change; it was not touched.
3. **Google.** The page read for this (Google's guide for client-side web applications) describes the *implicit* flow, which `CloudAuth` does not implement, and nothing read says a browser app may redeem an authorization code with PKCE and no client secret. Treat Google on the web as unresolved. **Microsoft** documents the route (a redirect address registered with the `spa` type makes the token endpoint answer cross-origin requests, and it refuses a client secret from a browser), so Microsoft is the provider the web could serve first. CORS on the storage endpoints (Graph, Azure Blob, S3, Drive, GCS, CloudKit) was not examined.

Credentials on the web would be held in memory only, as everything else is (the page's `KeyValueStore` is not persisted), so a reload signs the person out.

Checked: `:web:compileKotlinWasmJs` builds it. The callback page and the channel were exercised once in Chromium (a page opened the window, the window posted its address, the page received it whole, the window closed); that check is not committed and **no automated test covers the web launcher**, so `SWR-MG-19` (j) is reported as untested. Not checked: the launcher inside the built app, a real provider, a popup blocker, Safari and Firefox.

### 4c.7 Wired into the app

**What is wired.** `PlatformServices.authorizationLauncher` is a new member (null by default). Android supplies `NeurOneApplication.browserLauncher`, iOS `IosAuthorizationLauncher`, the computer `DesktopBrowser.launcher()` and the browser `WebAuthorizationLauncher`. `AppServices.cloudAuth` is a `CloudAuth` over the host's `httpTransport` and launcher, with a `CredentialStore` on the app's own `keyValueStore`, where `np.cloud.accounts` is a sealed key (`SWR-MG-16`) and a per-install one (`SWR-MG-01`); it is **null** on a host without a transport or a launcher. **The browser therefore has none**, because it has no transport (§4c.6). A test (`CloudAuthWiringTest`) checks that the credentials are not readable in the host's raw store.

**The registrations are build inputs.** `:shared` writes `CloudAuthBuildConfig.kt` (generated, untracked) from Gradle properties, falling back to environment variables; a provider whose required values are not all set is null, and its sign-in fails with `NOT_CONFIGURED` naming it. Values are escaped into string literals. Required: Google `cloudAuth.google.clientId` and `.redirectUri` (optional `.clientSecret`, for a desktop-type client only); Microsoft `cloudAuth.microsoft.clientId` and `.redirectUri` (optional `.oneDriveTenant`, `.azureTenant`); CloudKit `cloudAuth.cloudKit.container`, `.apiToken` and `.signInCallbackUri` (optional `.environment`, `.baseUrl`). The environment names are `CLOUDAUTH_` plus the same words in capitals with underscores (for example `CLOUDAUTH_GOOGLE_CLIENT_ID`). The redirect address must match the host that runs it (the manifest's scheme on Android, `http://127.0.0.1:<port>` on a computer, `<origin>/oauth-callback.html` on the web): **one build has one value per provider**, so a build for several hosts needs a registration each, and nothing here picks the right one per host. **A client ID is not a secret** and is compiled into the app; a Google client secret for a desktop client is not one either (Google says so for installed apps), but a secret that is one must not be set here.

**Not done.** No screen lets the person sign in or out; the backup route (§4c.9) is the only use of an account to open an `ObjectStore`; no client is registered at any provider; the per-host redirect problem above; the shared, desktop and web changes compiled here and the shared desktop tests pass, but the Android and iOS changes were written without an Android SDK or a Mac and are first built by CI, and nothing ran on a device.

### 4c.8 The cloud accounts screen

**Where.** Settings, under "Cloud accounts", on a host where `AppServices.cloudAccounts` is not null (a host with both an HTTP transport and a launcher; the browser has neither a transport nor, so far, a way to finish a sign-in, so it shows no entry). `CloudAccountsModel` (`:shared`, `life.neurone.shared.cloud`) holds the state and the actions; `CloudAccountsScreen` draws it.

**What it shows.** One card per `CloudService`: its name, a state (signed in; not signed in; the provider ended the sign-in, so sign in again; not set up in this version of the app) and the buttons that state allows. Google Drive and Google Cloud Storage are separate cards because they are separate grants (§4c.1). A provider with no registration in this build shows "not set up" and no button, so the person is not sent to a browser for a sign-in that cannot start (`CloudAuth.isConfigured`). Amazon S3 has no browser sign-in: "Add access keys" opens a form with the access key ID in the clear and the secret key and session token masked.

**What it does not show.** Every outcome is a fixed kind (`CloudNoticeKind`) with a string of its own, so no token, no provider text and no exception message can reach the screen. Closing the browser says nothing. Signing out always removes the credential from this device; when the provider has no revoke call, or the call failed, the notice says so and points to the provider's own settings, because **the app's access at the provider is then still there** (Microsoft and Apple have no revoke call used here; an Amazon key stays valid until deleted at Amazon). Credentials that cannot be read are reported and left alone.

**Tests.** `CloudAccountsModelTest` (9) drives the model over a real `CloudAuth` with a stand-in provider and browser: the list, an unregistered provider, one account per service, cancel and every failure kind, sign in again, sign out with and without a revoke call, Amazon keys, an unreadable store, one action at a time. `CloudAccountsScreenTest` (6) renders the screen: what is offered follows the registrations, a sign-in shows its outcome and then offers sign out, the Amazon form (masking, Save needs both fields, Cancel drops what was typed, Save shows the outcome), and the Settings entry. Taking the registration check out of the screen makes four of them fail. A UI test of a button below the window must scroll to it first: the AWS card is the last, and a click outside the window hits nothing (found when a test waited for a Save that was never pressed).

**Strings.** 34 new keys (`CLOUD_*`), English in all eleven locales; the translations come only through the verified import (`CLAUDE.md` §17.7), so every other language reads English here until then. The six service names are brands and are marked as not to be translated.

**Not done.** No provider is registered, so every browser sign-in reads "not set up" and only Amazon S3 can complete; the screen has been drawn only by the JVM test renderer, not on a device; a backup destination from an account is §4c.9; the wording of the notices has had no review by a person who is not its author; accessibility (screen-reader order and labels beyond the button text) has not been examined.

### 4c.9 The backup route

**What is chosen.** On the backup and restore screens a row says where the backup is kept: this device (the default, and the folder or file choices as before) or one of the signed-in accounts that need nothing beyond the sign-in, namely Google Drive (its application data folder), OneDrive (its app folder) and iCloud (the build's container). The choice is one account id under `np.backup.cloud-account`, per install, sealed with the other keys and never moved in a migration. `AppServices.backupPlace` is the cloud place while a choice stands, so the backup, the restore and the automatic backup all use it.

**What a cloud place is.** `CloudStores.storeFor` gives the account's adapter from `:cloudstore`; the credential is `CloudAuth`'s lazy one, so every call asks for a token and gets a fresh one, and a store built when a screen opened is good an hour later. A refused sign-in comes back as a 401, which the flow reports as "route unavailable".

**It carries a backup and nothing else.** `CloudStores.routeFor` promises **no exclusive create** for every service: a migration relies on one (`SWR-MG-07`) and none has been checked against a real account (`SWR-MG-11` (contract) has no test), so the core withholds a cloud place from a migration and the screen says the place keeps the health-data backup only. Google Drive could not promise one in any case. The recordings in the UHDR folder are **not** sent: every object crosses the store's calls whole, in memory, as hex, which is wrong for a recording (Gap 1, §2.2), so `MigrationPlace.carriesRecordings` is false for a cloud place and the backup and the restore both skip them.

**Choice and sign-in.** Signing out of the chosen account returns the backup to this device and drops the choice. A sign-in the provider ended does **not**: the place stays cloud, its calls fail with the sign-in status, and the row says to sign in again under Settings. Falling back to this device without a word would keep a backup where the person did not choose. An account whose sign-in was ended cannot be newly chosen.

**Tests.** `CloudStoresTests` (4, `:cloudauth`): the routes, which services are offered, the account's token going to the service and a fresh one after expiry, a refused sign-in, iCloud's container. `CloudBackupTest` (6) and `CloudBackupRowTest` (3, `:shared`): the choice and its persistence, the route and the recordings flag, the recordings left off a cloud place, a choice refused, sign-out against an ended sign-in, `AppServices.backupPlace`, and the row. Taking out the recordings guard, or letting a choice outlive its account, makes tests fail.

**Not done.** Google Cloud Storage, Azure Blob and Amazon S3 are not offered: they need a bucket or container, a region or an account typed in and kept, which has no screen. No provider is registered, so no browser sign-in completes in a real build and none of the three can be chosen yet. No adapter has run against a real account. The call timeout (120 s, `CloudStores.CALL_TIMEOUT_SECONDS`) has no measurement behind it (UC-115). A whole bundle goes through one call (Gap 1), so a very large one is untested. A direct upload-progress or cancel for a slow cloud backup is not built. Nothing ran on a device.
