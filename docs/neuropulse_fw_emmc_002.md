## §A — Warranty Token Architecture (replaces NP-FW-EMMC-001 Rev A §7 warranty owner ID references)

### A.1 Rationale

NP-PRIV-001 Rev A CRITICAL-01 identified that using a "warranty owner ID" as the SHDR-to-person linkage creates a re-identification path. The warranty registration system necessarily collects name, email, and address. If the warranty owner ID is a foreign key into that system, SHDR is person-linked and the UHDR/SHDR privacy separation fails.

### A.2 Warranty token definition

**Warranty token:** A 256-bit value generated by the device's TRNG at first activation, stored in the Config partition, transmitted as the sole device-to-person linkage in all SHDR uploads.

```c
/* firmware/warranty/np_warranty_token.h */
#define NP_WARRANTY_TOKEN_LEN   32  /* 256-bit */

typedef struct {
    uint8_t token[NP_WARRANTY_TOKEN_LEN];
    uint32_t generated_at_session;  /* session counter at generation — no timestamp */
    uint8_t reserved[28];           /* pad to 64 bytes */
} np_warranty_token_t;
```

### A.3 Token generation

Generated at first device activation (first successful USB-C pairing with the NeuroPulse app). Generated using the i.MX RT1062 TRNG peripheral with health tests per NIST SP 800-90B. Stored in the Config partition under the AES-256-XTS SHDR key (same key used for SHDR partition). Not stored in UHDR. Not derived from any user-identifying input.

### A.4 Warranty registration flow

1. App sends the warranty token (not the device serial number, not the user's email) to the warranty registration API.
2. Warranty registration system stores: `{warranty_token: <256-bit>, registered_name: <string>, registered_email: <string>, registered_address: <string>, serial_number: <string>, registration_date: <date>}`.
3. The warranty registration database and the SHDR fleet database are **separate database instances with no cross-database foreign keys**. The warranty_token is present in both, but joining them is prohibited in production.
4. A database-level constraint (enforced in the SHDR fleet DB schema) ensures the SHDR fleet DB contains no columns of types `VARCHAR(name)`, `VARCHAR(email)`, `VARCHAR(address)`, or any column whose name contains the strings `name`, `email`, `address`, `phone`, or `postal` (enforced at schema creation and validated in CI).

### A.5 No-join production rule

Production application code must not JOIN the warranty registration database and the SHDR fleet database in a single query. This is enforced by:
1. The two databases are in separate cloud projects / accounts with no shared IAM roles.
2. A CI test attempts a cross-database join and confirms it fails with an authorisation error.
3. Code review checklist item: "Does this query join warranty_db with shdr_db? If yes, requires Privacy Lead sign-off."

### A.6 Device factory reset — SHDR token clear

On factory reset (see §B below), the warranty token is cleared from the Config partition and a new TRNG token is generated. The new token is not pre-registered — the new owner must register. The SHDR fleet database record for the old token is archived (not deleted — needed for warranty history) and flagged `device_transferred: true`. No new SHDR records are written under the old token after the factory reset.

## §B — Device Factory Reset Procedure

### B.1 Rationale

NP-PRIV-001 Rev A HIGH-03 identified that no factory reset procedure exists for device transfer. Without a reset, a new owner's usage is associated with the previous owner's SHDR history, and UHDR ciphertext (though unreadable without the key) remains on the device.

### B.2 User-initiated factory reset

**Trigger:** User selects "Reset Device" → "Transfer or Sell Device" in the app's device management settings.  
**Authentication gate:** Requires current biometric authentication + explicit two-step confirmation ("This will permanently erase all your health data from this device. This cannot be undone." → "Erase Device").

### B.3 Reset sequence

The reset is orchestrated by the app via a signed reset command sent to the hub, which executes the following sequence in order:

```
R-1  App issues signed FACTORY_RESET command (Ed25519, same signing infrastructure as session descriptors)
R-2  Hub verifies signature — rejects unsigned reset attempts
R-3  Hub sets reset_in_progress flag in SNVS_LPGPR1 (survives warm reset)
R-4  Hub suspends all active sessions and closes all open file handles
R-5  Hub issues eMMC SANITIZE (CMD38, SANITIZE_START) on UHDR partition
     → NIST SP 800-88 "Purge" — all UHDR blocks overwritten to media-specific pattern
R-6  Hub zeroes SHDR partition (eMMC ERASE + SANITIZE)
R-7  Hub zeroes Config partition
R-8  Hub generates new TRNG salt (256-bit) for future UHDR Argon2id derivation
R-9  Hub generates new warranty token via TRNG (not pre-registered)
R-10 Hub writes only: new TRNG salt, new warranty token, and factory firmware defaults to Config partition
R-11 Hub clears reset_in_progress flag
R-12 Hub reboots — device presents as factory-new to the next owner
```

### B.4 Power-loss resilience

If power is lost during the reset sequence:
- Steps R-1 through R-3: reset has not started; on next boot, no reset occurs, user must reinitiate.
- Steps R-4 through R-9: `reset_in_progress` flag is set; on next boot, the bootloader detects this flag and re-issues SANITIZE and zero operations for all data partitions before completing boot. The device does not become usable until all SANITIZE operations complete.
- Steps R-10 through R-12: config writes are atomic (LittleFS transaction); if interrupted, LittleFS rolls back to the pre-write state and the bootloader re-runs step R-10 on the next boot.

### B.5 App-side factory reset

The iOS/Android app must also:
- Delete all locally cached session data, consent records, and device pairing information
- Remove the device from the user's cloud account (UHDR backup association)
- Notify the user: "Your device has been reset. All data has been erased from the device and from your NeuroPulse account."

## §C — Two-Layer UHDR Key Scheme

### C.1 Rationale

NP-PRIV-001 Rev A HIGH-03 identified that the single-layer Argon2id-derived key creates a lifecycle problem: biometric template changes render UHDR inaccessible; recovering requires re-encrypting the full partition. A two-layer scheme decouples the biometric from the bulk encryption key.

### C.2 Key architecture

```
Layer 1 — UHDR Master Key (UKMD):
  - 32-byte random value generated by TRNG at first device activation
  - Used directly as the AES-256-XTS key for the UHDR partition
  - Never transmitted off-device
  - Stored in Config partition encrypted under the Layer 2 wrapper key

Layer 2 — Master Key Wrapper Key (WKMD):
  - Derived from user's biometric/PIN using Argon2id (same parameters as NP-FW-EMMC-001 Rev A §6)
  - Used only to encrypt/decrypt the 32-byte UKMD stored in Config
  - Held in on-chip SRAM only during the unlock window (app foreground session)
  - Zeroed from SRAM using memset_explicit when app moves to background
```

### C.3 Config partition UKMD record

```c
/* Config partition offset 0x1000 — UKMD record */
typedef struct {
    uint8_t  ukmd_ciphertext[32];   /* AES-256-GCM(UKMD, WKMD, nonce=ukmd_nonce) */
    uint8_t  ukmd_nonce[12];        /* AES-GCM nonce — random, unique per wrap operation */
    uint8_t  ukmd_tag[16];          /* AES-GCM authentication tag */
    uint8_t  argon2id_salt[32];     /* Salt for WKMD derivation — device-unique, TRNG */
    uint32_t argon2id_version;      /* 0x13 = Argon2id version 1.3 */
    uint32_t argon2id_m_cost;       /* Memory: 65536 KiB (64 MiB) */
    uint32_t argon2id_t_cost;       /* Iterations: 4 */
    uint32_t argon2id_parallelism;  /* p = 1 */
    uint8_t  reserved[44];          /* Pad to 192 bytes — future use */
} np_ukmd_record_t;
```

### C.4 UKMD unlock sequence (on app foreground)

```
1. App prompts biometric / PIN
2. App sends biometric-derived input to i.MX RT1062 via secure USB-C protocol
3. i.MX RT1062 runs Argon2id(input, argon2id_salt, m=65536, t=4, p=1) → WKMD (32 bytes, in SRAM)
4. AES-256-GCM decrypt(ukmd_ciphertext, WKMD, ukmd_nonce) → authenticate tag → extract UKMD (32 bytes, in SRAM)
5. Mount UHDR partition using UKMD as AES-256-XTS key
6. Zero WKMD from SRAM (it is not needed after UKMD is derived)
7. UKMD is zeroed from SRAM when the app moves to background (not on session end — session end leaves UHDR mounted for the session log write)
```

### C.5 Biometric change / PIN change procedure

When the user changes their biometric enrollment or PIN:

```
1. User authenticates with the current biometric/PIN (UKMD is in SRAM after unlock, step C.4)
2. User provides new biometric/PIN
3. New WKMD = Argon2id(new_input, argon2id_salt, same cost parameters)
4. New nonce generated via TRNG
5. new_ukmd_ciphertext = AES-256-GCM encrypt(UKMD, new_WKMD, new_nonce)
6. Config partition UKMD record atomically updated (LittleFS transaction)
7. Zero new_WKMD from SRAM
8. UHDR partition ciphertext unchanged — only the 32-byte wrapper is re-encrypted
```

The UHDR partition (up to 6.9 GiB) is **never re-encrypted** during a biometric change. Only the 192-byte UKMD record in the Config partition changes. This operation completes in milliseconds.

### C.6 PIN fallback

PIN-based WKMD derivation is always available as a fallback when biometric is unavailable (device restart, biometric hardware failure, biometric lockout). The same Argon2id derivation applies with the PIN as input. There is no separate "PIN key" — the architecture is PIN-or-biometric → WKMD → UKMD.

## §D — Scratch Partition Encryption for Research Anonymisation

### D.1 Rationale

NP-PRIV-001 Rev A MEDIUM-04 identified that the Scratch partition's unencrypted nature creates a cleartext UHDR window during research anonymisation. During the anonymisation task, UHDR data is decrypted and written to Scratch for processing. If the device loses power mid-process, this plaintext data persists until next boot.

### D.2 Session key generation

Before the anonymisation task begins:

```c
/* firmware/anon/np_anon_scratch.h */

typedef struct {
    uint8_t  k_scratch[32];       /* AES-256-CTR key — in SRAM only */
    uint8_t  nonce[16];           /* CTR nonce — TRNG, unique per session */
    uint32_t session_id;          /* Anonymisation session counter */
    bool     key_valid;           /* Set to true after TRNG generation, false after zero */
} np_anon_scratch_ctx_t;

/* Called before any Scratch write */
np_status_t np_anon_scratch_init(np_anon_scratch_ctx_t *ctx) {
    /* Generate k_scratch and nonce from TRNG */
    TRNG_GetRandomData(TRNG0, ctx->k_scratch, 32);
    TRNG_GetRandomData(TRNG0, ctx->nonce, 16);
    ctx->key_valid = true;
    /* k_scratch and nonce are in SRAM only — not written to any partition */
    return NP_OK;
}
```

### D.3 Encrypted Scratch writes

All writes to the Scratch partition during anonymisation must use AES-256-CTR with the session key:

```c
np_status_t np_anon_scratch_write(np_anon_scratch_ctx_t *ctx,
                                   uint32_t block_offset,
                                   const uint8_t *plaintext,
                                   size_t len) {
    uint8_t ciphertext[NP_SCRATCH_BLOCK_SIZE];
    /* Counter = nonce || block_offset (big-endian) */
    np_aes_ctr_encrypt(ctx->k_scratch, ctx->nonce, block_offset, 
                       plaintext, ciphertext, len);
    return np_emmc_write_scratch(block_offset, ciphertext, len);
}
```

### D.4 Key zeroing

```c
void np_anon_scratch_complete(np_anon_scratch_ctx_t *ctx) {
    /* Compiler-barrier-protected zero */
    memset_explicit(ctx->k_scratch, 0, sizeof(ctx->k_scratch));
    memset_explicit(ctx->nonce,     0, sizeof(ctx->nonce));
    ctx->key_valid = false;
    /* Issue SANITIZE on Scratch partition blocks used in this session */
    np_emmc_sanitize_scratch();
}
```

### D.5 Atomic pipeline requirement

The anonymisation pipeline must be structured as an atomic transaction:
1. `np_anon_scratch_init()` — generate key
2. Read UHDR data → decrypt with UKMD → write to encrypted Scratch
3. Apply anonymisation transformations (k-anonymity, l-diversity, DP noise) on encrypted Scratch data
4. Validate anonymised extract (header field check, l-diversity check)
5. Write validated extract to output queue (encrypted with study-descriptor public key)
6. `np_anon_scratch_complete()` — zero key, SANITIZE Scratch

If any step fails, the entire sequence is aborted: key is zeroed, Scratch is sanitized, no extract is produced. The app notifies the user that anonymisation failed and must be retried. No partial extracts are ever placed in the output queue.

### D.6 Power-loss resilience

An `anon_in_progress` flag is set in SNVS_LPGPR2 at step D.5.1 and cleared at D.5.6. On boot, if this flag is set, the bootloader:
1. Issues SANITIZE on the Scratch partition before completing boot.
2. The k_scratch key is in SRAM only and is lost on power-off — even if Scratch is recovered before SANITIZE, it is unreadable without the key.

## §E — EDF+ Patient Header Policy

### E.1 Rationale

NP-PRIV-001 Rev A MEDIUM-05 identified that EDF+ files generated by clinical EEG tools typically contain patient name, date of birth, and other personal identifiers in the mandatory header fields. If NeuroPulse-generated EDF+ files follow clinical convention, every UHDR EDF+ file contains plaintext PII within the decrypted UHDR partition.

### E.2 NeuroPulse EDF+ header standard

All EDF+ files generated by NeuroPulse firmware must conform to the following header policy:

```
Header field         Required value                    Prohibited values
---------------------------------------------------------------------------
local patient id     [UHDR_TOKEN_16CHAR] X X X         Any real name, DOB, sex code
                     (first 16 chars of UHDR token,    other than 'X'
                     followed by three 'X' fields for
                     sex, birthdate, and patient name)

local recording id   Startdate DD-MMM-YYYY             Any clinician name,
                     NeuroPulse X                      any patient code other
                     NeuroPulse_v[FW_VER]              than opaque token

startdate            DD.MM.YY (preserved)              —

starttime            HH.MM.SS (preserved)              —
```

**EDF+ local patient identification field format (per EDF+ spec §2.1.3.1):**

```
[patient_code] [sex] [birthdate] [patient_name]
```

NeuroPulse format:
```
NP[UHDR_TOKEN_FIRST_14_CHARS] X X NeuroPulse_User
```

Example (token `a3f7b9c2d1e4f5a6b7c8d9e0f1a2b3c4`):
```
NPa3f7b9c2d1e4f5 X X NeuroPulse_User
```

### E.3 EDF+ writer implementation requirement

```c
/* firmware/edf/np_edf_writer.h */

/* Fills the EDF+ header patient and recording identification fields
   with privacy-preserving values per NP-FW-EMMC-002 §E.2.
   
   Parameters:
     header:      pointer to the 256-byte EDF header buffer
     uhdr_token:  the 32-byte device UHDR token (binary)
     fw_version:  NeuroPulse firmware version string
     session_ts:  session start timestamp (UTC)
*/
np_status_t np_edf_write_header(np_edf_header_t *header,
                                 const uint8_t *uhdr_token,
                                 const char *fw_version,
                                 time_t session_ts);
```

The function must:
1. Convert first 14 bytes of UHDR token to hex string → `patient_code` prefix "NP" + 14-char hex = 16 chars.
2. Set sex field to 'X'.
3. Set birthdate field to 'X'.
4. Set patient name to 'NeuroPulse_User'.
5. Set recording ID startdate from `session_ts` (DD-MMM-YYYY format).
6. Set recording ID hospital code to 'NeuroPulse'.
7. Set recording ID technician to 'X'.
8. Set recording ID equipment to `NeuroPulse_v` + `fw_version` (truncated to field width).

### E.4 Header validation in research anonymisation pipeline

Before any EDF+ file is included in a research extract, a header validator must run:

```c
np_status_t np_edf_validate_privacy_header(const np_edf_header_t *header) {
    /* Verify sex field is 'X' */
    if (header->local_patient_id[NP_EDF_SEX_OFFSET] != 'X') return NP_ERR_PRIVACY_HEADER;
    /* Verify birthdate field is 'X' */
    if (header->local_patient_id[NP_EDF_DOB_OFFSET] != 'X') return NP_ERR_PRIVACY_HEADER;
    /* Verify patient name field does not contain alphabetic chars beyond 'NeuroPulse_User' */
    if (np_edf_header_contains_real_name(header)) return NP_ERR_PRIVACY_HEADER;
    return NP_OK;
}
```

Any EDF+ file that fails this validation is excluded from the research extract and a `SHDR` fault event is logged: `EDF_PRIVACY_HEADER_VIOLATION`. The anonymisation task continues with remaining files (the pipeline is not aborted — only the offending file is excluded).

## §F — Mode F: Consent and Safety Specification

### F.1 Locked decisions (per NP-PRIV-REM-001 STEP-06)

The following are locked design decisions for Mode F (808-830nm bilateral retinal PBM during normal-looking wear):

1. **Default state:** Mode F is `DISABLED` in all shipping firmware. The user must take an explicit action to enable it.
2. **Consent requirement:** Mode F is a separately named, separately consented feature. It may not be enabled as part of general session consent. The consent screen must name the feature ("Invisible Retinal Light Therapy"), describe what it does (continuous NIR light during normal wear), state the dose range, and link to the IEC 62471 assessment.
3. **App toggle:** A dedicated per-device Mode F toggle exists in the app's device settings. Default: OFF. The toggle is not exposed in general session configuration.
4. **Ambient indicator — hardware:** When Mode F is active, the right temple amber LED enters a **triple-pulse pattern**: 3 pulses at 150ms on / 150ms off, followed by a 2-second pause, then repeat. This pattern is distinct from the normal in-session single-pulse pattern (which mirrors session frequency, per §4.7 of CLAUDE.md). The triple-pulse pattern is not suppressible by stealth mode — it is a safety indicator, not a status indicator.
5. **IEC 62471 cumulative dose:** The IEC 62471 retinal exposure assessment for Mode F must be calculated as **cumulative daily dose across all Mode F wear time per calendar day**, not as peak pulsed power per session. The firmware dose counter for Mode F (`mode_f_daily_joules_per_cm2`) resets at midnight UTC and prevents Mode F operation beyond the daily IEC 62471 limit.
6. **Regulatory gate:** Mode F must not be enabled in any shipping firmware until the RISK-03 regulatory opinion letter explicitly covers 808-830nm bilateral retinal PBM in Mode F operating conditions (see NP-REG-PBM1064-001 Rev B, Q-13). A firmware build flag `NP_MODE_F_REGULATORY_CLEARED = 0` must be set to `1` by the firmware gating process only after the opinion letter is received and reviewed.

### F.2 Firmware constants

```c
/* firmware/visual/np_mode_f.h */

/* Build-time gate — set to 1 only after RISK-03 opinion letter received */
#define NP_MODE_F_REGULATORY_CLEARED    0

/* Ambient indicator pattern (triple-pulse) */
#define NP_MODE_F_LED_ON_MS             150
#define NP_MODE_F_LED_OFF_MS            150
#define NP_MODE_F_LED_PULSES            3
#define NP_MODE_F_LED_PAUSE_MS          2000

/* Daily cumulative dose limit (J/cm²) — to be set by RISK-03 opinion */
/* PLACEHOLDER — must not be used in production firmware until cleared */
#define NP_MODE_F_DAILY_DOSE_LIMIT_J_CM2    0.0f  /* 0 = always blocked until cleared */

/* UHDR session classification */
/* Mode F active status is logged to UHDR: eye_open_during_mode_f: bool per 1-min interval */
/* Daily cumulative dose counter is logged to UHDR: mode_f_daily_dose_j_cm2 */
/* No Mode F data goes to SHDR */
```

### F.3 UHDR/SHDR classification for Mode F data

| Data element | Classification | Rationale |
|---|---|---|
| Eye-open/closed state during Mode F | UHDR | Reveals when user is wearing the device during daily activity |
| Mode F daily cumulative dose (J/cm²) | UHDR | Dose received is a health record |
| Mode F enabled/disabled state | SHDR (binary flag only) | Device configuration — no health content |
| Mode F session count (unsigned integer) | SHDR | Device usage metric — no timestamps, no dose values |

## §G — SHDR Accelerometer Data Reclassification

*(Added 2026-06-03 — NP-PRIV-001 Rev B finding MEDIUM-06. Addresses NP-PRIV-REM-001 STEP-10. BLOCKING for SHDR fleet DB schema freeze.)*

### G.1 Rationale

NP-PRIV-001 Rev B HIGH-01 (originally NP-PRIV-001 Rev A HIGH-01) confirmed that raw accelerometer series written to SHDR reveal motor-control patterns that are health-inferrable (Parkinson's, post-stroke hemiplegia, essential tremor). Only the derived maintenance signal is permitted in SHDR. This section specifies the permitted fields and prohibited fields so the SHDR fleet DB schema can be frozen correctly.

### G.2 Permitted SHDR fields (per session gap)

```c
/* SHDR accelerometer record — written once per between-session gap */
typedef struct {
    bool drop_detected;       /* true if peak g-force exceeded NP_ACCEL_DROP_THRESHOLD_G */
    bool maintenance_alert;   /* true if rolling drop rate exceeded NP_ACCEL_MAINT_THRESHOLD */
    uint8_t reserved[6];      /* pad to 8 bytes — future use */
} np_shdr_accel_record_t;
```

Default thresholds (factory firmware, configurable via signed OTA):
- `NP_ACCEL_DROP_THRESHOLD_G` = 15.0f (free-fall-equivalent impact)
- `NP_ACCEL_MAINT_THRESHOLD` = 3 drops in any rolling 7-day window

### G.3 Prohibited SHDR fields

The following must **never** appear in any SHDR record or SHDR fleet DB schema column:

| Prohibited data | Why prohibited |
|---|---|
| Raw accelerometer series (any axis, any unit) | Reveals motor control profile — health-inferrable |
| Peak g-force value | Reveals severity of impact — motor health inference |
| Average g-force | Same |
| RMS g-force | Same |
| Orientation vector at time of impact | Reveals posture/activity at time of fall |
| Timestamp of individual drop events | Correlates drops to user activity patterns |
| Drop count as an integer | Reveals cumulative motor difficulty over time |

### G.4 Fleet DB schema constraint

The SHDR fleet database schema must enforce these constraints at the schema definition level, before any data is written:

```sql
-- Correct schema: only boolean fields for accelerometer data
ALTER TABLE shdr_records ADD COLUMN drop_detected      BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE shdr_records ADD COLUMN maintenance_alert  BOOLEAN NOT NULL DEFAULT FALSE;

-- The following column types are prohibited for accelerometer data:
-- FLOAT, DOUBLE, REAL, NUMERIC, INTEGER (for counts), VARCHAR (for vectors)
-- Any column named: g_force, accel_*, orientation_*, drop_count, drop_timestamp
```

### G.5 CI schema test (OI-EMMC2-07)

A CI test must run against the SHDR fleet DB schema definition and fail if any of the following conditions are true:

```python
# ci/test_shdr_schema.py
PROHIBITED_COLUMN_PATTERNS = [
    r'g_force', r'accel_[xyz]', r'orientation', r'drop_count',
    r'drop_timestamp', r'impact_', r'fall_'
]
PERMITTED_ACCEL_COLUMNS = {'drop_detected', 'maintenance_alert'}

def test_no_raw_accelerometer_columns(schema_columns):
    accel_cols = {c for c in schema_columns if any(
        re.search(p, c, re.I) for p in PROHIBITED_COLUMN_PATTERNS
    )}
    assert not accel_cols, f"Prohibited accelerometer columns found: {accel_cols}"
```

This test is BLOCKING for SHDR fleet DB schema freeze. No schema migration may proceed until this test passes.

### G.6 On-device firmware module

Module `np_accel_shdr` (to be authored as part of STEP-10):

```c
/* firmware/shdr/np_accel_shdr.h */

/* Reads raw 3-axis accelerometer between sessions.
   Applies on-device thresholds. Writes only the two
   boolean fields to SHDR. Raw values are never written
   to any eMMC partition.
   
   Called by: np_hub_session_log (after session close)
   SHDR write: np_shdr_write_accel_record()
*/
np_status_t np_accel_shdr_process_session_gap(void);
```

The raw accelerometer buffer is allocated in SRAM only, processed in-place, and zeroed with `memset_explicit` before `np_accel_shdr_process_session_gap` returns. No intermediate values are written to any partition.
